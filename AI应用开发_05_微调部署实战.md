# 模型微调与部署实战：从LoRA到生产推理的全流程

## 一、参数高效微调技术谱系

### 1.1 LoRA的核心算法与工程实现

LoRA（Low-Rank Adaptation）的核心假设是：预训练模型在微调过程中的权重更新量 ΔW 具有低秩性。对于预训练权重矩阵 W₀ ∈ ℝ^{d×k}，LoRA将其更新约束为：

```
W = W₀ + ΔW = W₀ + BA,   B ∈ ℝ^{d×r}, A ∈ ℝ^{r×k}, r ≪ min(d,k)
```

前向传播时，h = W₀x + BAx。由于 B 和 A 的参数量 r(d+k) 远小于 dk，训练参数量可降至全量的 0.1%~1%。

**秩选择策略（r的选择）：**

- `r=1`：极端压缩，仅适用于极其简单的任务适配，如二元情感分类的头微调
- `r=8`（默认值）：大多数场景下效果与全量微调最接近的平衡点
- `r=16~64`：任务复杂度高（如多轮对话、代码生成）时可提升拟合能力，但显存占用线性增长
- `r=128+`：收益递减，通常不建议；此时应直接使用全量微调或 DoRA

经验法则：LoRA 参数量 = 2 × r × (d + k) × n_layers。对于 Llama 3 70B（80层，d=8192），当 r=8 时单层参数量约 131K，总参数量约 10.5M，仅为全量的 0.015%。

```python
import torch
import torch.nn as nn

class LoRALayer(nn.Module):
    """Low-Rank Adaptation layer for linear transforms.
    
    Args:
        in_dim: Input dimension of the original weight matrix
        out_dim: Output dimension of the original weight matrix  
        rank: Low-rank dimension r (typically 1-64)
        alpha: Scaling factor (alpha/rank controls the update magnitude)
    """
    def __init__(self, in_dim: int, out_dim: int, rank: int = 8, alpha: float = 16.0):
        super().__init__()
        self.rank = rank
        self.scaling = alpha / rank
        
        # A matrix: random Gaussian init (frozen during inference merge)
        self.lora_A = nn.Parameter(
            torch.randn(rank, in_dim) * 0.02  # std=0.02 for stable init
        )
        # B matrix: zero init so ΔW=0 at step 0 (no harmful initial shift)
        self.lora_B = nn.Parameter(torch.zeros(out_dim, rank))
        
        self.dropout = nn.Dropout(0.1)  # prevent co-adaptation with base weights

    def forward(self, x: torch.Tensor, base_output: torch.Tensor) -> torch.Tensor:
        """Apply LoRA update: output = W₀x + (α/r)BAx"""
        lora_update = self.lora_B @ self.lora_A  # (out_dim, in_dim)
        return base_output + self.dropout(x @ lora_update.T) * self.scaling
```

**Scaling Factor 的影响实验：**

`α/r` 控制更新步长。当 `α=16, r=8` 时 scaling=2.0。若 scaling 过大（>4），训练初期 loss 剧烈震荡；过小（<0.5）则收敛极慢。推荐范围内 `α=2r ~ 4r` 时最稳定。

**初始化策略的关键点：**

W_A 采用 Kaiming 均匀分布初始化，W_B 初始化为零。这确保训练开始时 ΔW=0，模型输出不受 LoRA 分支影响，避免破坏预训练分布。若 W_B 也用随机初始化，初始 loss 会飙升 3-5 倍，需要额外 warmup 补偿。

### 1.2 QLoRA: 4-bit量化时代的微调

QLoRA（Quantized LoRA）的核心贡献在于：**在不回传量化梯度的情况下，通过冻结的 4-bit 基模型计算前向loss，反向传播时反量化到 BF16 计算 LoRA 梯度**。

**NF4（4-bit NormalFloat）量化原理：**

NF4 假设权重服从零中心正态分布，通过分位数映射将连续的 float32 分布均匀映射到 16 个离散值：

```python
import bitsandbytes as bnb
from torch import Tensor

def nf4_quantize(weight: Tensor) -> tuple[Tensor, Tensor]:
    """4-bit NormalFloat quantization with double quantization.
    
    Args:
        weight: FP32 weight tensor
    Returns:
        quant: NF4 quantized weights (uint8 nibbles)
        absmax_fp32: per-block absolute maximum for dequant
    """
    # Step 1: Quantize — map normal distribution to 4-bit via CDF
    absmax = weight.abs().max(dim=-1, keepdim=True).values  # per-row
    normalized = weight / absmax  # now in [-1, 1]
    
    # NF4 lookup table: 16 equally-probable quantiles of N(0,1)
    nf4_levels = Tensor([
        -1.0, -0.696, -0.525, -0.394, -0.277, -0.169, -0.064, 0.039,
         0.144,  0.251,  0.362,  0.479,  0.607,  0.754,  0.935,  1.0
    ])
    
    # Scalar quantization to nearest level index
    indices = torch.bucketize(normalized, nf4_levels)  # [0, 15]
    quant = indices.to(torch.uint8)
    return quant, absmax
```

**双重量化（Double Quantization）：**

对 absmax 再做一次 8-bit 量化，将每块的缩放因子从 FP32（4字节）压缩到 INT8（1字节）。对 Llama 3 70B，假设块大小 64，absmax 数量为 8192/64 × 80 layers × 2 ≈ 20,480 → 从 80KB 降至 20KB。

**Paged Optimizer：**

当 GPU 显存不足时，优化器状态（Adam 的 momentum + variance）被换出到 CPU 内存。QLoRA 利用统一内存分页机制，仅在反向传播的梯度计算阶段换入必要页，使单卡 24GB 即可微调 Llama 3 8B。

**显存消耗对比（Llama 3 70B, batch_size=1, seq_len=4096）：**

| 方案 | 模型权重 | 梯度 | 优化器状态 | 激活值 | 总计 |
|------|----------|------|-----------|--------|------|
| 全量微调 (FP16) | 140 GB | 140 GB | 280 GB (Adam) | ~40 GB | ~600 GB |
| LoRA (BF16, r=8) | 140 GB | 0 (冻结) | ~20 MB | ~40 GB | ~180 GB |
| QLoRA (NF4, r=8) | 35 GB | 0 (冻结) | ~20 MB | ~40 GB | ~75 GB |
| QLoRA + Gradient Checkpoint | 35 GB | 0 | ~20 MB | ~4 GB | ~39 GB |

注意：LoRA 和 QLoRA 都需要额外的约 2×r×(d+k) 显存存放可训练的 LoRA 权重及对应优化器状态，但占总显存比例极低（~0.1%）。

### 1.3 Adapter架构：Series vs Parallel

**Series Adapter（序列适配器）：**

在 Transformer 的每层子层（Attention → FFN）后插入 bottleneck 结构：Down-projection (d → d_bottleneck) → Non-linear → Up-projection (d_bottleneck → d)。典型 bottleneck 维度 d_bottleneck = d/4。

典型实现（Houlsby et al., 2019）：

```python
class SeriesAdapter(nn.Module):
    """Series adapter inserted after each Transformer sublayer.
    
    Architecture: LayerNorm → DownProject (d→r) → ReLU → UpProject (r→d)
    """
    def __init__(self, d_model: int, bottleneck_ratio: float = 0.25):
        super().__init__()
        bottleneck = int(d_model * bottleneck_ratio)
        self.down = nn.Linear(d_model, bottleneck, bias=False)
        self.up = nn.Linear(bottleneck, d_model, bias=False)
        self.ln = nn.LayerNorm(d_model)
        
        # Near-zero init: up weight sampled from N(0, 0.01)
        nn.init.normal_(self.up.weight, std=0.01)
        
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        residual = x
        z = self.ln(x)
        z = self.down(z)
        z = torch.relu(z)
        z = self.up(z)
        return residual + z  # residual connection around adapter
```

**Parallel Adapter（并行适配器）：**

与主路径并行计算，输出相加。相比 Series 形式，并行架构在前向时延迟更稳定，因为 adapter 计算可与主路径同时进行。

```
# Series:  x → Sublayer → Adapter → x'
# Parallel: x → Sublayer → + → x'
#              → Adapter → ↑
```

关键差异：
- Series Adapter 改变信息流顺序（LayerNorm → Adapter → Sublayer → LayerNorm → Adapter），可能干扰预训练层的分布
- Parallel Adapter 更适合融合到已有推理框架中，移除 adapter 后模型完全恢复原状
- Series 在 NLP 任务上通常高 0.3~0.5% 的准确率，但推理引入额外串行延迟

### 1.4 Prompt Tuning与P-Tuning v2

**Prompt Tuning：** 在输入嵌入序列前插入 k 个可学习的虚拟 token 嵌入（维度同词嵌入）。问题在于：soft prompt 仅作用于输入层，无法改变中间层的表示——复杂度不够。

**P-Tuning v2：** 将可学习的 prompt 嵌入插入到每一层的 hidden state 中，而非仅输入层。

```python
class PTuningV2(nn.Module):
    """P-Tuning v2: learnable deep prompt tokens at each layer.
    
    Args:
        num_layers: Transformer layer count
        hidden_dim: Model hidden dimension
        prompt_length: Number of virtual tokens per layer (default 20)
    """
    def __init__(self, num_layers: int, hidden_dim: int, prompt_length: int = 20):
        super().__init__()
        # [num_layers, prompt_len, hidden_dim] — separate prompt per layer
        self.prompts = nn.Parameter(
            torch.randn(num_layers, prompt_length, hidden_dim) * 0.02
        )
        
    def forward(self, layer_idx: int, hidden: torch.Tensor) -> torch.Tensor:
        """Concatenate learned prompt tokens to hidden states at layer_idx."""
        prompt = self.prompts[layer_idx].unsqueeze(0)  # [1, prompt_len, d]
        prompt = prompt.expand(hidden.size(0), -1, -1)  # [B, prompt_len, d]
        return torch.cat([prompt, hidden], dim=1)
```

**技术局限：**
- Prompt Tuning 性能严重依赖 prompt 长度（15~20 token 为最佳，超出后收益递减）
- P-Tuning v2 在生成任务上效果接近 LoRA，但分类任务差距明显（约 1-2%）
- 两者都无法合并到模型权重中，推理时必须保留额外的 prompt token 路径，增加部署复杂度

### 1.5 2025年改进变体：DoRA / LoRA+ / rsLoRA

**DoRA（Weight-Decomposed Low-Rank Adaptation）：**

将权重分解为幅值 m 和方向 V/‖V‖，仅对方向分量应用 LoRA：

```
W' = m · (W₀ + ΔW) / ‖W₀ + ΔW‖
```

其中 m 是可学习的幅值向量，ΔW = BA 是 LoRA 更新。这更接近全量微调的实际更新模式（全量微调中方向和幅值是协变的）。实验表明：DoRA 在 r=4 时即可达到 LoRA r=16 的效果，参数效率提升 4 倍。

```python
class DoRALayer(nn.Module):
    """Weight-Decomposed LoRA: learns magnitude m and directional update BA."""
    def __init__(self, weight: nn.Parameter, rank: int = 8):
        super().__init__()
        self.weight = weight  # original frozen weight
        self.m = nn.Parameter(torch.norm(weight, dim=1, keepdim=True))  # magnitude
        
        # Standard LoRA matrices for direction update
        self.lora_A = nn.Parameter(torch.randn(rank, weight.size(1)) * 0.02)
        self.lora_B = nn.Parameter(torch.zeros(weight.size(0), rank))
        
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        base_dir = self.weight / self.weight.norm(dim=1, keepdim=True).detach()
        lora_dir = (self.lora_B @ self.lora_A)  # direction update
        merged_dir = base_dir + lora_dir
        merged_dir = merged_dir / merged_dir.norm(dim=1, keepdim=True)
        return x @ (self.m * merged_dir).T
```

**LoRA+（Learning Rate Asymmetry）：**

使用不同的学习率 η_B = 2~4 × η_A。因为 B（零初始化）和 A（随机初始化）处于不同的损失平面位置，B 需要更大的步长来追赶。默认设置 η_B=2×η_A，在 GSM8K 上提升约 1.5%。

**rsLoRA（Rank-Stabilized Scaling）：**

将 scaling factor 改为 α/√r 而非 α/r。根号缩放使各 r 值下 LoRA 更新的方差一致：

```
LoRA:  ΔW = BA,      Var(ΔW) ∝ r        → 随 r 增大方差增长
rsLoRA: ΔW = (α/√r)BA,  Var(ΔW) ∝ 1     → 与 r 无关的方差
```

这使得不同 r 的学习率可以共享，无需为每个 r 单独调优学习率。

**效果对比（MMLU, Llama 3 8B, r=8）：**

| 方法 | MMLU (5-shot) | 参数量 (M) | 训练时间 (A100h) |
|------|---------------|-----------|-----------------|
| 全量微调 | 68.4 | 8000 | 48 |
| LoRA | 67.1 | 10.5 | 12 |
| QLoRA | 66.8 | 10.5 | 18 |
| DoRA | 67.6 | 10.6 | 14 |
| LoRA+ | 67.3 | 10.5 | 12 |
| rsLoRA | 67.2 | 10.5 | 12 |

## 二、微调数据工程

### 2.1 指令格式规范化

数据格式对微调效果的影响常被低估。三种主流格式各有优劣：

**1. ShareGPT格式（多轮对话原始存储）：**

```json
{
  "conversations": [
    {"from": "system", "value": "You are a helpful assistant."},
    {"from": "human", "value": "What is attention?"},
    {"from": "gpt", "value": "Attention is a mechanism..."},
    {"from": "human", "value": "Can you elaborate?"},
    {"from": "gpt", "value": "Sure! In the Transformer..."}
  ]
}
```
优势：原生支持多轮、系统提示、工具调用；劣势：每轮训练时需动态拼接，padding/masking逻辑复杂。

**2. Template格式——嵌入特殊token的扁平化文本：**

```
<|im_start|>system
You are a helpful assistant.<|im_end|>
<|im_start|>user
What is attention?<|im_end|>
<|im_start|>assistant
Attention is a mechanism...<|im_end|>
```
优势：可直接用作 tokenizer 的输入，无结构化开销；劣势：手动维护模板字符串。

**3. Llama Chat格式（原生支持的ChatML变体）：**

```python
def format_llama_chat(messages: list[dict], tokenizer) -> torch.Tensor:
    """Format messages into Llama Chat template with proper loss masking.
    
    Only computes loss on assistant tokens — user/system tokens are masked.
    """
    tokens = []
    loss_mask = []
    
    bos = tokenizer.bos_token_id
    eos = tokenizer.eos_token_id
    
    for msg in messages:
        role, content = msg["role"], msg["content"]
        
        if role == "system":
            text = f"<|start_header_id|>system<|end_header_id|>\n\n{content}<|eot_id|>"
            mask_section = False
        elif role == "user":
            text = f"<|start_header_id|>user<|end_header_id|>\n\n{content}<|eot_id|>"
            mask_section = False
        elif role == "assistant":
            text = f"<|start_header_id|>assistant<|end_header_id|>\n\n{content}<|eot_id|>"
            mask_section = True  # ← only train on assistant responses
        
        ids = tokenizer.encode(text, add_special_tokens=False)
        tokens.extend(ids)
        loss_mask.extend([-100] * len(ids) if not mask_section else ids)
    
    return torch.tensor(tokens), torch.tensor(loss_mask)
```

**工程差异的关键点：**

- **Loss Masking**：只有 assistant 回复部分参与 loss 计算。若不对 user 和 system token 做 -100 mask，模型会学习"预测 user 输入"——破坏生成质量
- **EOS 的显式处理**：Llama Chat 格式要求每个 assistant 回复后加 `<|eot_id|>` 作为终止信号，否则模型在推理时无法自行停止
- **多轮 vs 单轮拼接效率**：ShareGPT 格式下需在线拼接对话历史，Template 格式则可预编码为 token IDs 批量缓存

### 2.2 数据质量自动筛选

**P3（Public Pool of Prompts）的方法——多样性优先：**

对每个数据点提取输入输出 tf-idf 特征，用 KMeans 聚类后从每个簇等比例采样，确保数据覆盖不同任务类型和领域。

**Deita（Data-efficient Instruction Tuning for Alignment）——难度和质量双维度评分：**

```python
def compute_deita_score(instruction: str, response: str, model) -> float:
    """Deita scoring: quality (LLM-as-judge) × difficulty (perplexity ratio).
    
    Args:
        instruction: User query
        response: Assistant response  
        model: Reference model (e.g., Llama 3 8B)
    Returns:
        Composite score in [0, 1]
    """
    # Quality score: ask an evaluator LLM on 4 dimensions
    quality_prompt = f"""Rate the response quality on a scale 1-5:
- Helpfulness: Does it solve the user's need?
- Relevance: Is every sentence on-topic?  
- Accuracy: Are there factual errors?
- Completeness: Does it cover necessary detail?

Instruction: {instruction}
Response: {response}
Score (1-5):
"""
    quality = query_llm(quality_prompt, model="gpt-4o-mini") / 5.0  # normalize
    
    # Difficulty score: perplexity ratio = PPL(output|model) / PPL(output|random)
    ppl_output = compute_perplexity(response, model)
    ppl_baseline = compute_perplexity(response, random_text_model)  
    difficulty = min(1.0, ppl_output / ppl_baseline)  # higher = harder
    
    return 0.6 * quality + 0.4 * difficulty
```

**ALPAGASUS——自动筛选逻辑：**

以 GPT-4 作为评判者，对每个 (instruction, response) 对从以下维度打分：是否包含有害内容、是否拒绝回答本应回答的问题、回复长度是否符合指令复杂度。淘汰得分最低的 50% 后，用剩余数据微调的模型在 MT-Bench 上得分反而更高（7.21 → 7.53），证明**数据质量远比数量重要**。

### 2.3 多轮对话数据的构造策略

策略1：**Flat concatenation** — 将所有轮次作为连续文本处理，loss mask 仅作用于最后一条 assistant 回复。优点是实现简单，缺点是无法学习到"对话历史"的模式。

策略2：**Progressive training** — 每条数据包含从第一轮到第 k 轮的历史，loss 作用于第 k 轮的 assistant 回复：

```python
def build_progressive_samples(conversation: list[dict]) -> list[dict]:
    """Build one training sample per conversation turn.
    
    Sample 1: [user_1, assistant_1] → loss on assistant_1
    Sample 2: [user_1, assistant_1, user_2, assistant_2] → loss on assistant_2
    Sample k: [user_1, ..., assistant_k] → loss on assistant_k
    """
    samples = []
    for i in range(1, len(conversation), 2):  # user-turn indexed from 1
        turn = i // 2 + 1  # which response turn this is
        history = conversation[:i+1]  # include response at index i
        samples.append({
            "messages": history,
            "train_on": f"assistant_{turn}"
        })
    return samples
```

策略3：**Random history truncation** — 训练时随机保留 40%~100% 的历史轮次。增强模型对丢弃上下文的鲁棒性。

### 2.4 数据配比优化

预训练数据 / 指令数据 / 偏好数据（Preference Data）的比例对最终模型质量至关重要。

**实验数据（基于 Llama 3 8B，SFT + DPO 两阶段）：**

| 预训练% | 指令% | 偏好% | MMLU | MT-Bench | AlpacaEval 2.0 |
|---------|-------|-------|------|----------|---------------|
| 0 | 100 | 0 | 63.2 | 6.54 | 15.3 |
| 10 | 80 | 10 | 65.1 | 7.02 | 21.4 |
| 20 | 60 | 20 | **66.8** | 7.31 | 28.7 |
| 30 | 40 | 30 | 66.2 | **7.38** | **30.1** |
| 50 | 25 | 25 | 65.4 | 7.12 | 25.6 |

关键发现：
- 完全基于指令数据微调会导致**灾难性遗忘**（Catastrophic Forgetting）
- 预训练数据占 20~30% 时，知识保持（MMLU）和对话质量（MT-Bench）达到帕累托最优
- 偏好数据配比超过 30% 后收益递减，甚至可能因数据量过大导致 DPO 训练不稳定

**推荐的批量配比方案：**

```python
def build_mixed_batch(
    pretrain_iter, 
    instruction_iter, 
    preference_iter, 
    batch_size: int = 32,
    ratios: tuple = (0.2, 0.6, 0.2)  # pre-train, instruction, preference
) -> dict:
    """Sample a mixed batch from three data sources with given ratios."""
    n_pretrain = int(batch_size * ratios[0])
    n_instruction = int(batch_size * ratios[1])
    n_preference = int(batch_size * ratios[2])
    
    return {
        "pretrain": next(pretrain_iter)[:n_pretrain],
        "instruction": next(instruction_iter)[:n_instruction],
        "preference": next(preference_iter)[:n_preference],
    }
```

## 三、全量微调的工程挑战

### 3.1 3D并行：TP + PP + DP

**Tensor Parallel（TP）——张量并行：**

将单个线性层的权重沿列/行方向切分到多个 GPU。以列并行（Megatron-LM 风格）为例：

```
# A = [A₁, A₂], 每块GPU持有Aᵢ
# forward: Z = X @ A = [X @ A₁, X @ A₂]  → 计算后 all-reduce 合并
```

TP 的优势在于极低的通信量（仅每个 Transformer 层一次 all-reduce），但受限于单机 GPU 数量（通常 ≤ 8）。典型实现：

```python
def column_parallel_linear(x: torch.Tensor, weight_chunks: list[torch.Tensor], 
                           rank: int, world_size: int) -> torch.Tensor:
    """Column-wise tensor parallel linear layer.
    
    Each GPU computes its slice of the output, then all-gather merges slices.
    """
    chunk = weight_chunks[rank]  # (out_dim / world_size, in_dim)
    local_out = x @ chunk.T  # (B, seq_len, out_dim / world_size)
    
    # All-gather across TP group to reconstruct full output
    full_out = torch.empty(x.size(0), x.size(1), -1, device=x.device)
    torch.distributed.all_gather_into_tensor(full_out, local_out)
    return full_out
```

**Pipeline Parallel（PP）——流水线并行：**

将模型层按阶段（stage）分配到不同 GPU，每个 GPU 计算连续的若干层。通信量极低（仅逐 micro-batch 传递激活和梯度），但 bubble 问题突出——即流水线排空时的 GPU 空闲。

分片策略：**分区均匀**分割（balanced partitioning）——计算每层的 FLOPs 和参数量，用动态规划找到负载最均衡的切分点。

```python
def partition_layers(layer_flops: list[float], num_stages: int) -> list[range]:
    """Partition Transformer layers into balanced stages for PP.
    
    Uses DP to minimize max FLOPS per stage while keeping each stage contiguous.
    """
    n = len(layer_flops)
    prefix = [0.0]
    for f in layer_flops:
        prefix.append(prefix[-1] + f)
    
    total = prefix[-1]
    target = total / num_stages
    
    partitions = []
    start = 0
    for stage in range(num_stages - 1):
        # Find the partition point closest to cumulative target
        end = min(
            range(start + 1, n),
            key=lambda i: abs(prefix[i] - prefix[start] - target)
        )
        partitions.append(range(start, end))
        start = end
    partitions.append(range(start, n))
    return partitions
```

**TP vs PP 的效率权衡：**

| 维度 | Tensor Parallel | Pipeline Parallel |
|------|----------------|-------------------|
| 通信粒度 | 每层一次 all-reduce | 每 micro-batch 一次点对点 |
| 通信量 | 大（O(hidden_dim × seq_len)） | 小（仅激活边界） |
| Bubble | 无 | 存在（约 15~30%） |
| 跨节点扩展 | 不推荐（NVLink 互连需求） | 可跨节点（RDMA） |
| 最佳场景 | 单机多卡（≤8） | 多机（8~64 GPU） |

3D 并行将这三种并行方式组合：**DP × PP × TP**。典型设置：DP=4, PP=4, TP=2，共 32 卡。

### 3.2 ZeRO Stage 1/2/3

ZeRO（Zero Redundancy Optimizer）解决的核心问题：优化器状态和数据并行梯度的冗余存储。

**ZeRO Stage 1：优化器状态分片**

```
# 传统DP：每卡完整保留 Optimizer States = 16ψ 字节
# ZeRO-1：每卡仅保留 1/N_dp 的 Optimizer States = 16ψ / N_dp 字节
# （ψ = 参数量，16 = fp32的4B × 2 states × 2 份副本）
```

**ZeRO Stage 2：梯度分片**

在 backward 完成后 all-reduce 梯度，但每卡仅保存自己分到的梯度分片，丢弃其他分片。

**ZeRO Stage 3：参数分片 + 梯度分片 + 优化器状态分片**

```python
def zero_stage3_memory_equation(param_count: int, dp_size: int) -> dict:
    """Compute per-GPU memory with ZeRO-3 partitioning.
    
    Assumptions:
        - FP16 weights: 2 bytes/param
        - FP32 optimizer states: 12 bytes/param (momentum + variance + fp32 copy)
        - Gradients: 2 bytes/param (FP16)
    
    Returns per-GPU memory in GB.
    """
    weight_bytes = 2 * param_count  # FP16
    grad_bytes = 2 * param_count    # FP16
    optimizer_bytes = 12 * param_count  # FP32 states
    
    # ZeRO-3: all quantities are partitioned across DP group
    per_gpu = {
        "weights": (weight_bytes / dp_size) / 1e9,
        "gradients": (grad_bytes / dp_size) / 1e9,
        "optimizer_states": (optimizer_bytes / dp_size) / 1e9,
        "total": (weight_bytes + grad_bytes + optimizer_bytes) / dp_size / 1e9,
    }
    
    # Without ZeRO-3 (full redundancy)
    no_zero = (weight_bytes + grad_bytes + optimizer_bytes) / 1e9
    per_gpu["vs_no_zero_saving"] = f"{no_zero / per_gpu['total']:.1f}x"
    
    return per_gpu

# Example: Llama 3 70B with DP=8
# {
#   "weights": 17.5 GB,     # 140 GB → 17.5 GB
#   "gradients": 17.5 GB,
#   "optimizer_states": 105 GB,
#   "total": 140 GB,         # vs 420 GB without ZeRO-3
#   "vs_no_zero_saving": "3.0x"
# }
```

**工程实现的通信权衡：**

ZeRO-3 每层 forward 前 need **all-gather** 参数，backward 后 need **reduce-scatter** 梯度。这部分通信延迟是无法隐藏的（相较于 ZeRO-2 只需 backward 后一次通信）。实际部署时，ZeRO-2 适合梯度累积步数多的大 batch 场景，ZeRO-3 适合模型参数量极大（>100B）的场景。

### 3.3 激活检查点

**Full Checkpointing：** 只保存每层输入，反向传播时从前向重算所有中间激活。

```
# 总激活内存：O(batch_size × seq_len × hidden_dim)
# Full checkpoint：仅 O(batch_size × seq_len × hidden_dim × layers) → O(batch_size × seq_len × hidden_dim)
# 即从保存所有层激活 → 仅保存输入激活
```

**Selective Checkpointing——选择性检查点：**

不是所有激活的重新计算代价都相同。Attention 的 softmax 输出（O(b²h)）比 FFN 的中间激活（O(bh²)）计算量小，但存储量大。最佳实践：**仅 checkpoint attention 中的 dropmask 和 softmax 输出，保留 FFN 激活**。

```python
def selective_checkpoint_policy(layer_type: str, hidden_dim: int, 
                                 seq_len: int) -> str:
    """Decide whether to checkpoint based on recomputation cost ratio.
    
    Decision rule: checkpoint if (memory_saved / recompute_cost) > threshold.
    """
    if layer_type == "attention":
        softmax_mem = seq_len ** 2 * 2  # FP16: 2 bytes
        softmax_flops = seq_len ** 2 * hidden_dim  # recompute cost
        ratio = softmax_mem / softmax_flops
        
        return "checkpoint" if ratio > 0.01 else "recompute"
    
    elif layer_type == "ffn":
        intermediate_mem = hidden_dim * 4 * hidden_dim * 2  # FFN intermediate
        intermediate_flops = hidden_dim * 4 * hidden_dim * hidden_dim
        ratio = intermediate_mem / intermediate_flops
        
        return "checkpoint" if ratio > 0.01 else "recompute"
    
    return "no_checkpoint"
```

**内存-计算权衡模型：**

```
Memory_saved = ∑(activation_size(l) - input_size)
Time_overhead_per_layer = 1.0 × forward_time (full) or 0.3× (selective)

# Llama 3 70B, bsz=4, seq=4096:
# No checkpoint:  ~120 GB activations
# Full checkpoint: ~8 GB activations, 28% training overhead
# Selective:      ~20 GB activations, 8% training overhead
```

### 3.4 梯度累积与混合精度训练

**梯度累积（Gradient Accumulation）：**

当 GPU 显存不足以支撑目标 batch 大小时，通过累积多个 micro-batch 的梯度来模拟大 batch：

```python
def train_with_gradient_accumulation(
    model, dataloader, optimizer, 
    micro_batch_size: int = 4, 
    accumulation_steps: int = 8
):
    """Simulate batch_size = micro_batch_size × accumulation_steps."""
    optimizer.zero_grad()
    
    for step, batch in enumerate(dataloader):
        loss = model(batch)
        loss = loss / accumulation_steps  # normalize for accumulation
        loss.backward()
        
        if (step + 1) % accumulation_steps == 0:
            # Clip gradients before optimizer step
            torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
            optimizer.step()
            optimizer.zero_grad()
            
            # Synchronize batch norm stats if applicable
            if hasattr(model, "sync_bn"):
                model.sync_bn()
```

**混合精度训练（Mixed Precision）的策略：**

BF16 优于 FP16 的原因在于其更大的指数范围（8位指数 vs 5位），不需要 loss scaling。Loss scaling 是指对 loss 乘以一个放大因子（如 2¹⁶），使梯度落入 FP16 可表示范围，再在权重更新时除以该因子。

```python
class MixedPrecisionTrainer:
    """BF16 mixed precision trainer with optional gradient scaling (FP16 fallback)."""
    def __init__(self, model, use_bf16: bool = True):
        self.use_bf16 = use_bf16
        self.scaler = torch.cuda.amp.GradScaler() if not use_bf16 else None
        
    def train_step(self, batch) -> torch.Tensor:
        if self.use_bf16:
            with torch.amp.autocast(dtype=torch.bfloat16):
                loss = self.compute_loss(batch)
            loss.backward()
            
        else:
            with torch.amp.autocast(dtype=torch.float16):
                loss = self.compute_loss(batch)
            self.scaler.scale(loss).backward()
            self.scaler.step(self.optimizer)
            self.scaler.update()
```

**batch size 分配策略的实践建议：**

- 目标 batch size = GPU 数 × micro-batch size × 梯度累积步数
- Llama 3 70B 训练推荐：64~256 的 batch size（以 token 计约 4M~16M tokens）
- small batch (< 32) 会导致 BatchNorm（若有）估计不准确，且梯度噪声大
- large batch (> 4096) 需要 learning rate warmup 延长，否则模型不收敛

## 四、强化学习微调工程

### 4.1 RLHF四组件架构

RLHF 的四个模型及其显存分配：

| 组件 | 角色 | 参数初始化 | 是否可训练 | 显存占用 | 精度 |
|------|------|-----------|-----------|---------|------|
| Policy (πθ) | 生成回复，被优化 | 来自 SFT checkpoint | 是 | ~140B × 2B = 280GB | FP16 |
| Reward (Rφ) | 对回复评分 | 来自偏好数据训练 | 否 | ~70B × 2B = 140GB | FP16 |
| Value (Vψ) | 估计状态价值（critic） | 从 Reward 初始化 | 是 | ~70B × 2B = 140GB | FP16 |
| Reference (πref) | 保存原始 policy | 来自 SFT checkpoint | 否 | ~70B × 2B = 140GB | FP16 |

**典型显存配置（Llama 3 70B, 8×A100 80G, ZeRO-3）：**

四组件同时加载需 280 + 140 + 140 + 140 = 700 GB，8×80=640 GB —— 超出。实际通过**参数卸载**（Parameter Offloading）解决：将 Reward 和 Reference 卸载到 CPU，训练 batch 前换入 GPU 计算 KL penalty。

**PPO算法的LLM实现变体：**

LLM 场景下 PPO 的主要改动：

```python
def ppo_train_step(
    policy, value, reward, ref_model, 
    query_batch: torch.Tensor,
    ppo_epochs: int = 4, 
    clip_eps: float = 0.2,
    kl_coef: float = 0.04
) -> dict:
    """Single PPO update over a batch of prompts.
    
    Key LLM-specific adaptations:
    1. KL penalty as soft constraint (not clipped reward)
    2. Masked loss for variable-length sequences
    3. Importance sampling clipping for multiple PPO epochs
    """
    # Generate responses from current policy (no grad)
    with torch.no_grad():
        response_ids = policy.generate(query_batch, max_new_tokens=512)
        response_log_probs = policy.log_probs(query_batch, response_ids)
        
        # KL penalty: D_KL(πθ || πref) at each token
        ref_log_probs = ref_model.log_probs(query_batch, response_ids)
        kl_div = torch.exp(response_log_probs - ref_log_probs) - 1
        kl_div = kl_div - (response_log_probs - ref_log_probs)  # unbiased estimator
        
        # Reward from reward model
        r = reward(response_ids)
    
    # PPO importance sampling loop
    advantages = []
    for epoch in range(ppo_epochs):
        current_log_probs = policy.log_probs(query_batch, response_ids)
        ratio = torch.exp(current_log_probs - response_log_probs.detach())
        
        # Clipped surrogate objective
        clipped_ratio = torch.clamp(ratio, 1 - clip_eps, 1 + clip_eps)
        pg_loss = -torch.min(ratio * advantages, clipped_ratio * advantages).mean()
        
        # KL penalty (adaptive)
        kl_penalty = kl_coef * kl_div.mean()
        total_loss = pg_loss + kl_penalty
        
        total_loss.backward()
    
    return {"policy_loss": pg_loss.item(), "kl": kl_div.mean().item()}
```

### 4.2 DPO的直接优化

DPO（Direct Preference Optimization）的核心洞察：**RLHF 的 reward 函数可以解析表示为 policy 和 reference policy 的 log ratio**。

**DPO Loss 实现细节：**

```python
def dpo_loss(
    policy_logps_chosen: torch.Tensor,    # log πθ(y_w | x)
    policy_logps_rejected: torch.Tensor,  # log πθ(y_l | x)
    ref_logps_chosen: torch.Tensor,       # log πref(y_w | x)
    ref_logps_rejected: torch.Tensor,     # log πref(y_l | x)
    beta: float = 0.1                     # temperature for implicit reward
) -> torch.Tensor:
    """Direct Preference Optimization loss.
    
    L_DPO = -E[log σ(β * (log(πθ(y_w)/πref(y_w)) - log(πθ(y_l)/πref(y_l))))]
    """
    # Implicit reward: β * log(πθ(y) / πref(y))
    pi_logratios = policy_logps_chosen - policy_logps_rejected
    ref_logratios = ref_logps_chosen - ref_logps_rejected
    
    logits = beta * (pi_logratios - ref_logratios)
    loss = -torch.nn.functional.logsigmoid(logits).mean()
    return loss
```

**DPO vs RLHF 的对比实验数据（基于 Llama 3 8B）：**

| 维度 | PPO (RLHF) | DPO | 说明 |
|------|-----------|-----|------|
| MT-Bench | 7.12 | 7.08 | 统计不显著 |
| AlpacaEval 2.0 | 26.3% | 25.8% | DPO略低 |
| 训练稳定性 | 需调 5+ 超参数 | 仅 β 需要调 | DPO显著简单 |
| 训练所需 GPU 时 | 24h (8×A100) | 8h (8×A100) | 无需值函数 |
| 对数据质量的敏感度 | 低 | 高 | DPO对偏好噪声敏感 |
| 实现复杂度 | 高（4模型+PPO loop） | 低（2模型+交叉熵） | |

DPO 的主要劣势：当偏好数据存在大量噪声或标注不一致时，DPO 会放大这些噪声（因为它在等式中直接使用了偏好标签）。RLHF 的 reward model 作为缓冲器，对噪声有更好的容忍度。

### 4.3 GRPO：去Critic的组相对策略优化

GRPO（Group Relative Policy Optimization）是 DeepSeek-R1 的核心 RL 方法。其关键创新是**用 group-based reward 替代 critic 网络**。

```python
def grpo_loss(
    policy, 
    prompts: torch.Tensor,
    group_size: int = 8,           # responses per prompt
    reward_fn,                      # rule-based + model-based reward
    beta: float = 0.04,             # KL penalty coefficient
    epsilon: float = 0.2            # clipping threshold
) -> torch.Tensor:
    """Group Relative Policy Optimization.
    
    For each prompt, sample G responses and compute group-relative advantage.
    No critic/value model needed — advantage is (r_i - mean(r_1..G)) / std(r_1..G).
    """
    total_loss = 0.0
    
    for prompt in prompts:
        prompt = prompt.unsqueeze(0).expand(group_size, -1)
        
        # Step 1: Sample G responses from current policy
        with torch.no_grad():
            responses = policy.generate(prompt, max_new_tokens=2048)
        
        # Step 2: Compute group-relative advantage
        rewards = torch.tensor([reward_fn(r) for r in responses])
        advantages = (rewards - rewards.mean()) / (rewards.std() + 1e-8)
        
        # Step 3: Compute policy gradient with KL penalty
        for i in range(group_size):
            log_probs = policy.log_probs(prompt[i], responses[i])
            old_log_probs = log_probs.detach()
            
            ratio = torch.exp(log_probs - old_log_probs)
            clipped = torch.clamp(ratio, 1 - epsilon, 1 + epsilon)
            
            # Surrogate objective with group-relative advantage
            surrogate = -torch.min(ratio * advantages[i], clipped * advantages[i])
            
            # KL penalty (per token)
            ref_log_probs = policy.ref_log_probs(prompt[i], responses[i])
            kl_penalty = beta * torch.exp(log_probs - ref_log_probs)
            kl_penalty = kl_penalty - beta * (log_probs - ref_log_probs)
            
            total_loss = total_loss + surrogate.mean() + kl_penalty.mean()
    
    return total_loss / len(prompts)
```

**GRPO vs PPO 的关键架构差异：**

1. **无 Value/Critic 模型**：节省 1/4 的显存（Llama 3 70B 约 140GB）
2. **Group-level 归一化**：advantage 在同一 prompt 的多个 response 间归一化，消除了 reward 分布的跨 prompt 方差影响
3. **响应级多样性**：group_size=8 时，模型强制生成多样化的回复策略——低分路径被抑制，高分路径被放大

DeepSeek-R1 在 GRPO 训练中采用了混合 reward：正确性奖励（rule-based 数学验证） + 格式奖励（是否用 `<think>` 标签） + 语言一致性奖励。纯 RL（无 SFT 阶段）即可涌现出长链推理能力。

### 4.4 KL散度控制

**Adaptive KL Controller 的工程实现：**

KL penalty 系数 β 不应固定。过大的 β 使 policy 无法偏离 reference（学不到新东西），过小的 β 则导致 reward hacking（生成高 reward 但无意义的文本）。

```python
class AdaptiveKLController:
    """Adjusts KL coefficient to keep KL divergence near target.
    
    Mechanism:
    - If actual KL > target_kl: increase β (penalize harder)
    - If actual KL < target_kl: decrease β (allow more exploration)
    """
    def __init__(self, init_kl_coef: float = 0.02, target_kl: float = 3.0):
        self.kl_coef = init_kl_coef
        self.target_kl = target_kl
        
    def step(self, current_kl: float) -> float:
        """Adjust KL coefficient based on exponentially smoothed KL deviation."""
        error = current_kl - self.target_kl
        # PID-like controller: proportional adjustment with damping
        adjustment = 0.01 * error
        
        self.kl_coef = max(0.001, min(0.5, self.kl_coef * (1 + adjustment)))
        return self.kl_coef
```

实践经验：target_kl=3~10（以 nats/token 为单位），β 范围在 0.005~0.1 之间。训练过程中 KL 会先快速上升（模型探索新回复模式），随后缓慢下降（收敛到优化区域）。

### 5.2 GPTQ与AWQ

**GPTQ（Post-Training Quantization via Optimal Brain Quantization）：**

基于近似二阶优化的权重量化方法。逐列量化权重矩阵，每量化一列后根据 Hessian 信息补偿量化误差。

**AWQ（Activation-Aware Weight Quantization）：**

观察发现：权重中少量"salient channels"（对应 Activation 大的通道）对量化更敏感。AWQ 通过 per-channel 缩放保护这些 salient channels，而非均匀量化。

```python
def awq_scale_factors(weight: torch.Tensor, activation: torch.Tensor, 
                       alpha: float = 0.5) -> torch.Tensor:
    """Compute per-channel scale factors for AWQ.
    
    Salient channels are those with larger activation magnitudes.
    Scale = max(1, (activation_abs_mean) ^ alpha) — protects important channels.
    """
    abs_mean = activation.abs().mean(dim=(0, 1))  # [hidden_dim]
    normalized = abs_mean / abs_mean.mean()
    
    # Scale factor = 1.0 for normal channels, >1 for salient channels
    scale = torch.pow(normalized, alpha).clamp(min=1.0, max=10.0)
    return scale
```

**NVIDIA vs AMD 的适配差异：**

| 维度 | NVIDIA (CUDA) | AMD (ROCm) |
|------|--------------|------------|
| GPTQ kernel | 原生支持（exllama kernel） | 需用 HIP 转换，性能约 85% |
| AWQ kernel | 原生支持（TensorRT-LLM 集成） | ROCm 5.7+ 支持，但 batch size > 1 时性能下降 ~20% |
| 4-bit 推理 | 所有 SMs 支持 | MI250/MI300 优秀，RX 系列不推荐 |
| 实际建议 | 推荐 AWQ | 推荐 GPTQ（AMD 侧优化更好） |

### 5.3 ONNX导出与算子兼容性

### 6.2 负载均衡

**Least Connections vs Token-based 路由：**

```python
class TokenBasedLoadBalancer:
    """Route requests to the GPU node with the lowest pending token count.
    
    More precise than least-connections for LLM serving, because:
    - A request with 4K prompt tokens is ~10x more expensive than 512-token one
    - Connection count alone cannot capture this disparity
    """
    def __init__(self, backends: list[str]):
        self.backends = backends
        self.pending_tokens: dict[str, int] = {b: 0 for b in backends}
    
    def select_backend(self, estimated_prompt_tokens: int) -> tuple[str, int]:
        """Select backend with minimal pending token load."""
        backend = min(self.pending_tokens, key=self.pending_tokens.get)
        self.pending_tokens[backend] += estimated_prompt_tokens
        return backend, self.pending_tokens[backend]
    
    def complete_request(self, backend: str, tokens_used: int):
        """Deduct consumed tokens after completion."""
        self.pending_tokens[backend] = max(
            0, self.pending_tokens[backend] - tokens_used
        )
```

对比实验：在 4 节点 Llama 3 70B 集群上，Token-based 策略的 P99 延迟比 Least Connections 低 35%（340ms vs 520ms）。

### 6.3 动态批处理

**Continuous Batching vs Static Batching：**

Static Batching：每批请求必须同时到达，等所有请求完成后才返回。存在**等待延迟**和**垃圾填充**（padding）——短的序列被长的序列拖慢。

Continuous Batching（vLLM 的核心创新）：每个 iteration 动态决定哪些序列继续生成、哪些已完成退出、哪些新请求加入。

```python
class ContinuousBatchingScheduler:
    """Iteration-level scheduling for continuous batching.
    
    At each decoding step:
    1. Remove completed sequences from the batch
    2. Add waiting requests if GPU memory permits
    3. Execute one forward pass over the current batch
    """
    def __init__(self, max_batch_tokens: int = 4096):
        self.running_seqs: list[Sequence] = []
        self.waiting_queue: list[Sequence] = []
        self.max_batch_tokens = max_batch_tokens
    
    def schedule(self) -> list[Sequence]:
        """Build the batch for the next iteration."""
        # Step 1: Eject finished sequences
        self.running_seqs = [s for s in self.running_seqs if not s.finished]
        
        # Step 2: Fill from waiting queue (best-effort packing)
        current_tokens = sum(s.num_tokens for s in self.running_seqs)
        
        while self.waiting_queue:
            candidate = self.waiting_queue[0]
            candidate_tokens = candidate.num_tokens
            
            if current_tokens + candidate_tokens > self.max_batch_tokens:
                break  # GPU memory cap reached
            
            self.waiting_queue.pop(0)
            self.running_seqs.append(candidate)
            current_tokens += candidate_tokens
        
        return self.running_seqs
```

**延迟-吞吐权衡实验数据（Llama 3 70B, A100-80G, TP=4）：**

| 策略 | 吞吐量 (tokens/s) | P50延迟 (ms) | P99延迟 (ms) | GPU利用率 |
|------|-------------------|-------------|-------------|----------|
| Static Batch=1 | 320 | 180 | 250 | 35% |
| Static Batch=8 | 1200 | 820 | 2100 | 85% |
| Continuous Batch | 1500 | 310 | 680 | 92% |

Continuous Batching 在同样的硬件上实现了 25% 的吞吐提升和 3x 的 p99 延迟降低。

**Repacking vs Padding：**

Padding：将所有序列 pad 到当前 batch 中最长序列长度。浪费约 30~50% 的计算。
Repacking：将短序列的 token 重新排列，填入其他序列的 padding 空间（Orca 论文中的方法）。实现复杂但可节省 15~25% 的计算量。

### 6.4 Auto Scaling

**基于请求队列深度和 GPU 利用率的弹性伸缩：**

```python
class AutoScaler:
    """Horizontal pod autoscaler for LLM inference.
    
    Scale up: when queue depth > threshold for sustained period.
    Scale down: when GPU utilization < 30% for sustained period.
    """
    def __init__(
        self,
        min_replicas: int = 1,
        max_replicas: int = 16,
        scale_up_threshold: int = 50,    # pending requests
        scale_down_threshold: float = 0.3,  # GPU utilization
        cooldown_seconds: int = 60,
    ):
        self.min_replicas = min_replicas
        self.max_replicas = max_replicas
        self.scale_up_threshold = scale_up_threshold
        self.scale_down_threshold = scale_down_threshold
        self.cooldown = cooldown_seconds
        self.last_scale_time = 0.0
    
    def decide(self, metrics: dict) -> str:
        """Decide scaling action based on current metrics."""
        queue_depth = metrics["queue_depth"]
        avg_gpu_util = metrics["avg_gpu_util"]
        current_replicas = metrics["replicas"]
        timestamp = metrics["timestamp"]
        
        # Cooldown check
        if timestamp - self.last_scale_time < self.cooldown:
            return "noop"
        
        # Scale up: queue growing
        if queue_depth > self.scale_up_threshold and \
           current_replicas < self.max_replicas:
            self.last_scale_time = timestamp
            return "scale_up"
        
        # Scale down: low utilization + minimal queue
        if avg_gpu_util < self.scale_down_threshold and \
           queue_depth < 10 and \
           current_replicas > self.min_replicas:
            self.last_scale_time = timestamp
            return "scale_down"
        
        return "noop"
```

**统计显著性检验：**

```python
from scipy import stats

def compare_models(baseline_scores: list[float], new_model_scores: list[float]) -> dict:
    """Paired bootstrap test for model comparison.
    
    Returns p-value and effect size (Cohen's d).
    """
    import numpy as np
    
    # Paired bootstrap: resample with replacement, compute mean diff
    n_bootstrap = 10000
    observed_diff = np.mean(new_model_scores) - np.mean(baseline_scores)
    
    bootstrap_diffs = []
    for _ in range(n_bootstrap):
        idx = np.random.choice(len(baseline_scores), size=len(baseline_scores), replace=True)
        b_diff = np.mean(np.array(new_model_scores)[idx] - np.array(baseline_scores)[idx])
        bootstrap_diffs.append(b_diff)
    
    # Two-sided p-value: proportion of bootstrap diffs with sign opposite to observed
    p_value = np.mean(np.abs(bootstrap_diffs) >= np.abs(observed_diff))
    
    # Cohen's d
    pooled_std = np.sqrt(
        (np.std(baseline_scores)**2 + np.std(new_model_scores)**2) / 2
    )
    cohens_d = observed_diff / pooled_std if pooled_std > 0 else 0.0
    
    return {
        "observed_diff": observed_diff,
        "p_value": p_value,
        "cohens_d": cohens_d,
        "significant": p_value < 0.05,
    }
```

```python
        model = self.treatment if arm == "treatment" else self.control
        response = model.generate(prompt)
        
        self.results[arm]["requests"] += 1

        return min(
            self.results["control"]["requests"],
            self.results["treatment"]["requests"]
        ) >= self.min_sample
```

```python
class CanaryRelease:
    """Gradual traffic migration with automatic rollback on metric degradation.
    
    Stages: 5% → 20% → 50% → 100% (each stage with monitoring window).
    """
    def __init__(self, current_model, candidate_model, 
                 monitor: MetricsMonitor):
        self.current = current_model
        self.candidate = candidate_model
        self.monitor = monitor
        
        self.stages = [0.05, 0.2, 0.5, 1.0]
        self.current_stage = 0
    
    def advance_stage(self) -> bool:
        """Move to next canary stage if metrics are healthy."""
        if self.current_stage >= len(self.stages):
            return False  # fully rolled out
        
        # Check candidate's metrics vs baseline
        candidate_p50 = self.monitor.get_p50_latency("candidate")
        baseline_p50 = self.monitor.get_p50_latency("current")
        
        # Auto-rollback if latency degradation > 20%
        if candidate_p50 > baseline_p50 * 1.2:
            self.rollback()
            return False
        
        self.current_stage += 1
        self.canary_weight = self.stages[self.current_stage]
        return True
    
    def rollback(self):
        """Full rollback: reset traffic to current model."""
        self.canary_weight = 0.0
        self.current_stage = 0
        print("Canary rollback triggered — metrics exceeded threshold")
```

```python
            "hyperparameters": metadata.get("hyperparameters"),
            "eval_results": metadata.get("eval_results"),
            "parent_version": metadata.get("parent_version"),  # lineage tracking
            "status": "staging",  # staging → production → deprecated
        }
        self.versions.append(version)
        self._save_registry()
    
    def promote_to_production(self, model_id: str):
        """Promote a version to production after evaluation gate passes."""
        for v in self.versions:
            if v["model_id"] == model_id:
                v["status"] = "production"
            elif v["status"] == "production":
                v["status"] = "deprecated"  # only one active prod version
        self._save_registry()
    
    def get_production_model(self) -> str | None:
        """Get currently active production model ID."""
        for v in self.versions:
            if v["status"] == "production":
                return v["model_id"]
        return None
```

**端到端的热切换流程：**

1. 候选模型通过所有离线评估（MMLU、GSM8K、MT-Bench）
2. 触发金丝雀发布（5% → 验证24h → 20% → 验证12h → 50% → 验证6h → 100%）
3. 金丝雀期间持续监控：P50/P99 延迟、错误率、用户留存率
4. 任何指标超出基线 20% 时自动回滚
5. 100% 切换后保持蓝绿集群 72h 作为快速回滚窗口
6. 更新模型版本注册表，标记旧版本为 deprecated
