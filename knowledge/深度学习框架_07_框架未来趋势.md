# 深度学习框架：框架未来趋势与前沿框架解析

## 1. 深度学习框架的历史演进

深度学习框架的发展可划分为四个关键时代，每个时代对应一种核心设计哲学的统治与更迭。

**第一代：符号计算图的开创（2007–2013）**。2007年，蒙特利尔大学Bengio实验室发布的**Theano**开创性地将符号化计算图（Symbolic Computation Graph）与自动微分（Automatic Differentiation）引入深度学习[1]。用户先定义符号表达式构建静态计算图，再编译执行。这一设计奠定了此后五年框架设计的基础范式。Theano的核心贡献不在于性能，而在于概念验证——它证明了"定义-编译-运行"的分离模式可以支撑梯度下降训练。但符号图的调试极度困难：无法在中间层插入print语句，断点无从谈起，用户面对的是一个完全坍缩的黑箱。2013年，伯克利贾扬清发布的**Caffe**以语言无关的协议缓冲区（Protocol Buffers）定义网络结构（prototxt文件），卷积模型的Layer配置成为可读、可交换的文本格式[2]。Caffe在计算机视觉社区迅速普及，但其架构深度绑定CNN场景，对RNN/Transformer等动态结构的支持基本为零。同年，**Torch**（Lua语言）凭借其灵活的张量库和命令式风格在小众研究圈层获得认可，但Lua语言的生态限制使其未能进入工业界。

**第二代：静态图的工业级统治（2015–2017）**。Google于2015年开源**TensorFlow 1.x**，以静态数据流图（Static Dataflow Graph）为核心[3]。TF1将Theano的符号图理念推向工业级规模：分布式执行引擎、多设备自动放置、生产级 serving 基础设施（TensorFlow Serving）。这让TF1成为工业部署的事实标准。但其学习曲线同样陡峭——用户必须先构建完整的符号图再执行，动态控制流需要`tf.cond`和`tf.while_loop`等特殊算子，调试如同蒙眼编程。社区将此称为"Curve Learning"——一条陡峭得反常的学习曲线。

**第三代：动态图的直觉革命（2017–2020）**。2017年1月，FAIR（Facebook AI Research）开源**PyTorch**，以动态计算图（Define-by-Run）和Eager执行模式彻底改变了深度学习框架的用户体验[4]。用户可以用原生Python控制流编写网络，在每个前向步骤即时构建图结构，Autograd引擎自动追踪操作用于反向传播。调试变得自然——可以插入任意print/断点。这种"以直觉写代码"的设计让PyTorch在学术社区迅速扩散：不到三年时间，NeurIPS论文中使用PyTorch的比例从个位数飙升至80%以上。TF2在2019年被迫转向默认Eager模式并融合Keras为高阶API，但TF1/TF2的API断层导致了巨大的生态断代，大量TF1代码无法平滑迁移。

**第四代：编译优先与函数式范式（2018至今）**。Google于2018年发布**JAX**，以函数式编程（Functional Purity）+ XLA即时编译（JIT Compilation）为核心理念[5]。JAX的函数是无状态的：`y = f(x)`不修改任何外部状态，随机性必须通过显式传入的PRNGKey控制。这移除了并行化的最大障碍——隐式全局状态。JAX的`jax.jit`将Python函数编译为XLA HLO，`vmap`自动向量化批处理维度，`pmap`在多个TPU/GPU上自动分布计算。这些原语的统一设计使JAX在TPU利用率和分布式训练效率上显著超越PyTorch和TF。PyTorch则通过2.x版本引入`torch.compile`回应编译浪潮，通过TorchDynamo捕获Python帧图、PrimTorch简化IR、Inductor生成Triton内核的三阶段流水线，实现了动态图的JIT编译优化[6]。

**核心趋势**：从静态→动态→编译融合。三个阶段并非线性替代，而是螺旋式演进：静态图的可优化性被JIT编译以新形式继承，动态图的易用性成为框架的基线要求。2025年后的框架不再争论"静态vs动态"，而是在动态语义上叠加编译优化层——PyTorch 2.x的Dynamo、JAX的JIT、TensorFlow的XLA殊途同归，都指向"动态编写、静态编译"的统一范式。

## 2. PyTorch的框架深入分析

### 2.1 整体代码架构

PyTorch的软件栈从高层到底层可分为五层：

**Torch API层（Python前端）**：`torch.nn`提供Module/Linear/Conv等高层抽象；`torch.optim`提供优化器；`torch.utils.data`提供DataLoader；`torch.distributed`提供分布式通信接口。这一层是用户直接交互的界面，代码量约15万行Python。

**ATen（A Tensor Library）**：PyTorch的C++核心张量库，实现所有基础张量操作（add、matmul、convolution、softmax等）的CPU/GPU版本。ATen通过代码生成技术——从`native_functions.yaml`的算子描述自动生成各后端（CPU/CUDA/Metal）的调度入口和类型分发代码[7]。每个算子在ATen中注册为一个`Tensor& operator()(Tensor&, const Tensor&)`的C++函数，自动推导设备分发。

**C10（Core Tensor Infrastructure）**：统一类型/设备抽象层。`c10::ScalarType`枚举所有数据类型（float32/bfloat16/float16/int8等），`c10::Device`统一表示CPU/CUDA/MPS/IPU等设备。C10的核心机制是**DispatchKey**——每个算子的执行路径通过DispatchKeySet决定：AutogradCPU、AutogradCUDA、SparseCPU、QuantizedCPU等Key组成位图，算子在分发时按Key优先级链式派发[8]。这实现了device-agnostic的算子调度。

**TorchScript / JIT编译器**：PyTorch的静态图IR层。TorchScript通过Tracing（`torch.jit.trace`——跟踪实际执行路径记录计算图）和Scripting（`torch.jit.script`——直接解析Python源码生成语法IR）两种方式将动态图转化为静态`Graph`对象[9]。该IR经过优化（常量折叠、算子融合、死代码消除）后通过ONNX导出或LibTorch（C++运行时）实现序列化部署。

**Autograd引擎**：自动微分系统。每个Tensor关联一个`grad_fn`（派生自`Node`），在前向传播时以函数为节点构建反向计算图（DAG）。反向传播时，引擎从`loss.grad_fn`出发拓扑排序遍历，调用每个`Node::apply()`计算梯度并累积到`tensor.grad`。引擎支持多线程梯度累加、延迟执行、以及梯度检查点（checkpointing）的内存优化。

**c10d（分布式通信库）**：封装NCCL（NVIDIA）、GLOO（CPU）、MPI后端，提供`all_reduce`、`broadcast`、`all_gather`等集合通信原语。`torch.distributed`在此之上构建了DistributedDataParallel（DDP）、FullyShardedDataParallel（FSDP）、以及RPC的分布式训练三件套[10]。

### 2.2 动态图与JIT的关系

PyTorch的Eager模式并非完全不构建图——每次前向执行时，Autograd引擎同时构建反向计算图（用于梯度传播）。但此图是**隐式、短暂的**：仅存在于反向传播期间，反向完成后即丢弃。这是"动态"的本质含义。

TorchScript通过Tracing和Scripting将这种隐式图**显式化、持久化**为静态IR。Tracing适用于不包含数据相关控制流的模型（如CV分类网络），Scripting适用于包含复杂控制流（`if/for`）的模型（如Transformer解码中的循环）。后者依赖TorchScript编译器对Python字节码子集的解析——这意味着并非所有Python语法都能通过，导致兼容性困境。

### 2.3 torch.compile的Dynamo编译机制

PyTorch 2.x引入的`torch.compile`是框架演进中的一个里程碑[6]。其工作流程分为三个阶段：

**第一阶段：TorchDynamo图捕获**。Dynamo在Python帧（Frame）层级hook解释器的执行，通过CPython的`PyEval_SetProfile`或PEP 523的Frame Evaluation API，在每次Python函数调用时检查当前帧。当检测到可优化的代码区域（如整个前向函数），Dynamo通过分析字节码自动提取子图——无需用户标注`@torch.jit.script`。未被覆盖的"碎图"仍然以Eager模式运行，保证100%正确性。

**第二阶段：PrimTorch IR简化**。捕获的计算图被降级到PrimTorch——一个由约250个原子算子（prim ops）组成的稳定IR层。这一抽象将PyTorch的2000+算子压缩到一个精简集合，使得后端编译器的适配工作从O(2000)降为O(250)。任何后端只需要实现这250个原语就能支持PyTorch。

**第三阶段：Inductor后端代码生成**。Inductor以PrimTorch IR为输入，经过算子融合（垂直融合、水平融合、逐点融合）、循环合并、内存规划等优化，最终通过Triton原语生成高效的GPU内核代码[11]。Triton是一种类Python的语言，用于编写GPU内核。Inductor生成的内核通过块级（block-level）调度优化，充分利用GPU的共享内存和寄存器，在Transformer类模型上达到了手动编写内核的90–110%性能。

`torch.compile`的关键价值在于：用户不需要改变任何模型代码，只需添加`model = torch.compile(model)`即可获得平均40–60%的训练加速和2–3倍的推理加速。这标志着PyTorch从"纯动态"进化到"动态编写、静态编译"的融合范式。

## 3. TensorFlow 2.x与Keras新生态

### 3.1 灾难性断代

TensorFlow 1.x的设计决策——默认静态图——在其发布之初是合理的工程选择。静态图允许全局优化、设备自动放置和分布式执行。但这个选择付出了**易用性的全部代价**。当PyTorch在2017–2019年间以Eager模式席卷研究社区时，TensorFlow的活跃用户大量流失。

Google在2019年发布的TF 2.0做出了代价巨大的转向：默认开启Eager模式，废除`tf.Session`、`tf.Graph`、`tf.placeholder`等TF1核心API，将Keras整合为官方推荐的高阶API。结果造成了一场"框架内的断代"——大量TF1代码面临重写。社区的信任受损：许多团队转向PyTorch，理由不是性能而是"不想再经历一次迁移"[12]。根据2020–2021年的多项调查，NeurIPS论文中PyTorch的使用率已超过80%，而TF降至不足15%。

### 3.2 Keras Core：多后端统一

2023年发布的Keras Core（后更名为Keras 3）是TensorFlow生态体系中最引人注目的战略回调。其核心承诺：相同的Keras API代码可以在PyTorch、JAX、TensorFlow三个后端上运行[13]。

实现机制是**后端适配器抽象层**。每个Keras层（如`keras.layers.Dense`）在内部不直接调用任何框架操作，而是通过后端适配器调用后端特定的实现。例如`Dense.call()`会路由到`backend.matmul()`，而`backend.matmul()`根据当前选定的后端分发到`torch.matmul`、`jax.numpy.dot`或`tf.matmul`。

跨框架复用的意义远超API便利：用户在开发阶段可以用PyTorch后端（利用其丰富的生态工具链），部署时切换到TensorFlow后端（利用TFLite/ TF Serving/ XLA优化），或在TPU训练时切换到JAX后端。Keras Core实质性打破了框架锁定。截至2025年，此策略正在逐步恢复TensorFlow生态的吸引力。

### 3.3 XLA编译优化

XLA（Accelerated Linear Algebra）是TensorFlow生态的编译器基础设施。其工作方式为：将TensorFlow计算图编译为HLO（High-Level Optimizer）IR，经过算子融合、内存布局优化、并行为设备无关优化，最后通过LLVM或TPU指令发射为设备代码[14]。

对于静态形状的模型（如ResNet-50在小批量下的计算图），XLA的算子融合可以显著减少内核启动次数和显存带宽消耗，加速比可达2–5倍。但对动态形状（如变长序列的BERT推理），每次形状变化触发重新编译，代价往往超过优化收益。这是XLA应用的主要限制——Google通过"编译缓存"和"形状打满"（shape padding）策略缓解，但未根本解决。

## 4. JAX：函数式框架的前沿

### 4.1 函数式纯函数（Functional Purity）

JAX最深刻的哲学抉择是**函数纯正性**：任何JAX函数不得修改输入的状态，`y = f(x)`保证不会对`x`产生副作用。这一点在传统框架中看似简单实则影响深远。

传统框架（PyTorch/TF）中，随机数生成器维护隐式全局状态。两次调用`torch.randn()`返回不同结果——不可预测、不可重现。而在JAX中，随机数操作必须显式传入PRNGKey：

```python
key = jax.random.PRNGKey(42)
key, subkey = jax.random.split(key)
x = jax.random.normal(subkey, (3,))
```

这确保了**参照透明性**（Referential Transparency）——相同的输入始终产生相同的输出。移除隐式全局状态使得并行变得天然安全：没有线程间竞争随机状态的隐患，函数可以安全地在多个设备上重复执行[15]。

### 4.2 JIT编译：`jax.jit`

`jax.jit`将纯JAX函数编译为XLA HLO的优化计算图：

```python
@jax.jit
def f(x):
    return jnp.sin(x) + jnp.cos(x)
```

首次调用时，JIT编译器追踪函数执行、捕获计算图、调用XLA优化并发送到GPU/TPU执行。后续调用命中编译缓存。对形状固定的函数（如固定批量大小的前向推理），jit编译可以带来10–100倍的加速——因为XLA的算子融合消除了大量内核启动开销。

动态形状问题在JAX中同样存在：形状变化的输入导致重新编译。JAX通过`jax.jit(static_argnums=...)`指定静态参数来缓解此限制。

### 4.3 自动微分：`jax.grad`

`jax.grad`从任意可微的JAX函数返回其梯度函数：

```python
def loss_fn(w, x, y):
    pred = predict(w, x)
    return jnp.mean((pred - y) ** 2)

grad_fn = jax.grad(loss_fn)  # 返回无状态梯度函数
gradients = grad_fn(w, x, y)
```

由于函数无状态，`jax.grad`可以自然地与`jax.jit`组合：

```python
@jax.jit
def train_step(w, x, y, lr):
    grads = jax.grad(loss_fn)(w, x, y)
    return w - lr * grads
```

这种组合的灵活性在实现复杂损失函数（如GAN对抗损失、对比学习损失、MoE负载均衡损失）时无与伦比。用户可以用纯Python表达式编写任意复杂的微分逻辑，JAX自动处理高阶偏导数和链式法则的代码生成。

### 4.4 vmap与pmap：高级并行设施

**`vmap`（向量化映射）**自动将处理单个样本的函数扩展到批处理版本。例如，`vmap(loss_fn, in_axes=(0, 0, 0))`自动在批量维度上并行计算损失，效果等价于手动编写批处理实现但无需修改原函数。这消除了手动管理批处理维度的巨大工程负担。

**`pmap`（并行映射）**将函数自动复制到多个设备（GPU/TPU）上，每个设备处理输入的一个分片，并通过集合通信同步结果。对于多TPU训练，JAX的pmap配合`jax.lax.psum`/`jax.lax.all_gather`提供了比PyTorch DDP更低延迟的同步语义[16]。

JAX的高级并行原语（jit + vmap + pmap + pjit）组成了一套**统一的编程模型**，端到端覆盖了从单设备函数开发到多TPU分布式训练的所有场景。这种设计的核心优势在于概念一致性：用户学会三个变换（grad/jit/vmap），就学会了JAX的全部并行和微分原语。

### 4.5 JAX生态圈

JAX的生态在DeepMind和Google Brain的推动下快速成长：

- **Flax**（Google Brain）：轻量级神经网络库，提供Module/Linen抽象，官方实现GPT、ResNet、ViT、Swin-Transformer等模型。
- **Haiku**（DeepMind）：类似`nn.Module`但基于函数式组合的库，DeepMind大部分公开研究（Perceiver、AlphaFold 2早期的演进版本）基于此。
- **Optax**：梯度变换和优化器库，实现AdamW、LAMB、Adafactor、Schedule-Free等50+优化器。
- **NumPyro**：概率编程库，基于Pyro的函数式重写，利用JAX JIT实现MCMC数千倍的采样加速。
- **RLax**：强化学习损失函数和算子库。[17][18]

JAX + Flax在新近研究界（尤其是DeepMind、Google Brain、以及AI初创公司如Anthropic的大量架构实验）中已成为首选框架。

## 5. 框架间的互操作与生态系统

### 5.1 ONNX：跨框架的桥梁

ONNX（Open Neural Network Exchange）由Microsoft和Facebook于2017年联合推出，旨在建立深度学习模型的中间表示标准[19]。其核心设计：

- **IR格式**：以protobuf序列化计算图。ONNX IR定义了一套标准算子集（约200+op），包括Conv、BatchNormalization、Gemm、Attention等。
- **导出流程**：用户通过`torch.onnx.export`将PyTorch模型转换为ONNX模型；TensorFlow通过`tf2onnx`工具链导出。
- **运行时推理**：ONNX Runtime（Microsoft）作为跨硬件推理引擎，支持CPU/GPU/DirectML/CoreML/NNAPI等后端，提供统一的推理API。

ONNX的实际价值在于"训练→部署"的解耦：用户可以在PyTorch（或JAX/Flax）中训练模型，导出为ONNX后使用ONNX Runtime部署到边缘设备、移动端或云端推理服务，无需在目标平台上安装训练框架。

但ONNX的局限性同样显著：对动态形状的支持有限、自定义算子的标准化流程缓慢、不同框架导出特定算子的兼容性需要持续维护。截至2026年，ONNX仍然是最广泛采用的中间表示格式，但对越来越复杂的动态模型（如LLM推理的场景化随机采样），ONNX覆盖力有所不足。

### 5.2 safetensors：安全格式的胜利

PyTorch原生的`.pt`文件使用Python pickle序列化，存在严重安全隐患：pickle可以在加载时执行任意代码。HuggingFace在2022年推出的**safetensors**格式解决了这一问题[20]。其设计极其简洁：文件仅包含张量元数据（数据类型、形状、偏移）和原始权重数据（连续内存块），不包含任何可执行代码。加载时使用零拷贝读取（zero-copy memory mapping），既安全又高效。

到2025年，safetensors已成为HuggingFace模型库的主要分发格式，几乎所有热门模型（Llama、Mistral、Qwen、DeepSeek等）都提供safetensors权重。PyTorch也在2.x中提供了对safetensors的原生加载支持。

### 5.3 量化、剪枝与蒸馏的原生支持

各框架在模型压缩工具链上的竞争日益激烈：

- **PyTorch**：`torch.quantization`支持训练后量化（PTQ，Post-Training Quantization）和量化感知训练（QAT，Quantization-Aware Training），通过`torch.ao.quantization`模块提供int8/fp16权重量化、动态量化、以及静态量化。`torch.pruning`提供结构化/非结构化剪枝。
- **JAX/Praxis**：通过`praxis.optimizers.MixedPrecisionTransform`自动处理混合精度策略；配合Flax的`fp32_weights/bf16_compute`配置实现训练时的精度控制。
- **TensorFlow Lite**：提供最完善的移动端量化工具链——训练后动态范围量化、全整数量化、float16量化。TFLite Converter在模型格式转换和部署优化方面成熟度最高。[21]

### 5.4 分布式训练支持

- **PyTorch**：`torch.distributed`提供DDP（数据并行）、FSDP（全分片数据并行）、以及RPC-Pipeline（流水线并行）三件套。FSDP通过ZeRO-3风格的参数分片将大模型训练扩展到数千GPU，PyTorch 2.x的`DTensor`进一步实现了通用的张量分片抽象[22]。
- **TensorFlow**：`tf.distribute.Strategy`提供了统一的分布式策略API——`MirroredStrategy`（单机多卡数据并行）、`MultiWorkerMirroredStrategy`（多机多卡同步训练）、`TPUStrategy`、`ParameterServerStrategy`。
- **JAX**：`pmap` + `pjit`的组合覆盖了数据并行、模型并行、以及两者的混合（SPMD，Single Program Multiple Data）。JAX的分布式设计以数组分片和聚合通信为原语，无需像PyTorch那样在多个抽象层间切换。[23]

## 6. 新平台和新场景的框架需求

### 6.1 训练到部署的全流程简化

AI生产系统要求训练、部署、监控的统一。这种需求催生了框架层面的端到端解决方案：

- **PyTorch + TorchServe**：提供模型版本管理、REST/gRPC推理API、日志记录、自动缩放等生产级特性。2024–2025年，PyTorch通过TorchRec扩展推荐系统部署、通过TorchSnapshot简化大模型状态管理。
- **TFX（TensorFlow Extended）**：更完备的生产ML平台——数据验证（TFDV）、特征工程（Transform）、训练（Trainer）、模型评估（Evaluator）、部署（Serving）的完整流水线。[24]
- **JAX + Vertex AI + XLA**：Google Cloud上JAX模型的训练+TPU推理的全托管流水线，在2023–2025年间被多家AI公司用于生产级LLM部署。

### 6.2 大模型训练的框架挑战

百亿到千亿参数的语言模型对框架提出了前所未有的性能要求：

- **FSDP（Fully Sharded Data Parallel）**：PyTorch官方的ZeRO-3实现，通过将模型参数、梯度、优化器状态分片到所有设备上，使单卡显存从上百GB降至数GB。2024年的FSDP 2.0引入`DTensor`原生分片支持，避免了FSDP 1.x的`_shard_wrapped_module`的复杂实现。
- **Megatron-LM**（NVIDIA）：针对百亿到万亿参数模型的专属训练框架，通过张量并行（Tensor Parallelism）+流水线并行（Pipeline Parallelism）+数据并行的3D并行组合，在NVIDIA DGX SuperPOD上实现了数百PFLOPS的有效训练吞吐[25]。
- **DeepSpeed**（Microsoft）：基于ZeRO的优化三部曲（ZeRO-1/2/3）加上ZeRO-Offload（将优化器状态卸载到CPU内存）、MoE支持（ZeRO++）、以及自动调优的梯度累积策略。DeepSpeed在Llama-2、Mixtral等模型的训练中广泛使用。[26]

这些框架的共同趋势是**多层并行的组合与调度**——不再依赖单一并行策略，而是根据模型架构、硬件拓扑、通信带宽自动组合数据并行、张量并行、流水线并行、序列并行等多种策略的叠加。

### 6.3 硬件多样化的适配

框架对非NVIDIA硬件的支持正在快速扩展：

- **CPU推理优化**：Apple M系列通过MLX框架——Apple官方推出的NumPy-like框架，利用MPS（Metal Performance Shaders）和统一内存架构实现高效的CPU/GPU混合推理。llama.cpp几乎兼容所有主流硬件（x86/ARM/Metal/CUDA）的大模型推理。Intel oneDNN和oneAPI提供x86 CPU上的深度学习加速。
- **多厂商GPU支持**：AMD ROCm已经能够运行主流的PyTorch和TensorFlow工作负载，包括LLaMA和Stable Diffusion的微调。Intel通过SYCL和oneAPI提供跨Intel GPU的加速。Apple Metal GPU在JAX和PyTorch的MPS后端支持下逐步成为Mac用户的主力推理硬件。[27]

硬件多样化的关键使能技术是**中间IR的抽象能力**。MLIR（Multi-Level Intermediate Representation）作为多层次编译器基础设施，允许下层硬件后端（LLVM/SPIR-V/PTX/CUBIN）插入统一的优化管线，而框架只需将计算图降到MLIR的特定Dialect（如`linalg`、`tosa`、`sparse_tensor`）。Google/XLA、Intel/Triton后端、AMD/ROCm编译器均基于MLIR生态构建，这暗示了未来框架将演变为MLIR前端，硬件适配将下沉到MLIR Dialect层[28]。

## 7. 2026年框架展望

### 7.1 Mojo：为AI而生的语言

Mojo由Chris Lattner（LLVM、Swift、Clang的创始人）创立的Modular公司开发，目标是以一种语言覆盖AI开发的全栈——从模型开发到部署推理，从数据预处理到高性能内核编写[29]。

Mojo的核心设计：

- **基于MLIR**：Mojo不是Python，而是在MLIR基础设施上构建的新语言。它提供了Python-like的语法——意味着Numpy、Torch、JAX的用户可以速通——但编译后可以达到接近C的速度和显存控制。
- **直接调用Python模块**：Mojo支持`from python import ...`直接无缝导入Python生态的任意库（NumPy、Torch、Pandas等）。这解决了新语言最严峻的冷启动问题——开发者不需要等待Mojo生态成熟，可以随时利用Python积累的数十万个库。
- **系统级控制**：支持手动内存管理、SIMD向量化、强类型泛型、编译器内置并行原语（`@parallel`/`@parameter`）。早期基准测试显示，在图像处理、张量运算等场景下比Python有1000–4000倍的加速[30]。
- **AI硬件原生支持**：Mojo编译器通过MLIR可以直达任何硬件后端的Dialect（GPU Nvidia→NVVM/PTX、AMD→ROCDL、TPU→StableHLO），无需中间框架层。

Mojo的真正价值在于**统一栈的愿景**：未来AI开发者可能不再需要在Python写逻辑 + C++写内核 + CMake构建系统 + CUDA写GPU代码 + ONNX做格式转换之间切换。Mojo试图用一个语言和编译器覆盖从研究原型到生产部署的全过程。2025–2026年，Mojo仍处于早期普及阶段，生态工具链尚不成熟，但其方向已引起行业广泛关注。

### 7.2 MLX：Apple的统一框架

MLX是Apple于2023年12月开源的多功能深度学习框架[31]。其核心设计哲学与JAX高度一致——函数式、延迟计算、自动微分——但针对Apple Silicon（M系列芯片）的统一内存架构深度优化。MLX的特性：

- **统一内存（Unified Memory）**：这是MLX区别于所有其他框架的最大优势。在Apple M系列芯片上，CPU和GPU共享同一物理内存池，无需在CPU和GPU之间复制张量数据。这消除了传统深度学习框架中最大的性能瓶颈——PCIe带宽限制的数据传输。
- **NumPy-like API**：MLX的API设计尽可能贴近NumPy，使得从原型到生产几乎没有认知负担。
- **JIT编译**：通过`@mlx.jit`实现函数级编译，利用MPS后端生成Metal Shader实现的优化GPU内核。

MLX已经成为Apple生态内LLM推理和微调的首选框架。mlx-lm项目（基于MLX的LLM推理库）支持Llama、Mistral、Qwen、DeepSeek等主流模型在M系列芯片上的高效运行，部分场景达到每秒30–50 tokens的推理速度。至2026年，MLX在Apple开发者和本地AI推理社区中持续扩大影响力。

### 7.3 框架的编译与执行统一

到2026年，一个清晰的趋势已经形成：所有主流框架都在走向**编译为先的AI Pipeline**。

- PyTorch 2.x的TorchDynamo + PrimTorch + Inductor不是可选的优化，而是框架的未来架构——从训练到部署的图级别编译。随着`torch.export`用于稳定模型导出、`AOTInductor`用于训练前编译部署，PyTorch正在系统性地将Eager模式"编译化"。
- JAX的JIT从一开始就是将Python函数编译为设备代码——编译不是附加优化，而是JAX核心的执行模式。JAX从诞生就是"编译为先"的框架。
- TensorFlow的XLA、Keras 3的JAX后端、TFLite的Converter——都将模型转化为编译IR后再执行。

这背后的根本驱动力是**AI模型的规模化**：当模型达到千亿参数、训练集群达到数千GPU/TPU时，粗粒度的Eager执行效率无法满足需求。框架必须将计算图抽象为可全局优化的IR序列，在编译阶段进行算子融合、内存规划、通信调度——这些优化无法在逐算子执行的Eager模式中实现[32]。

### 7.4 2026年的框架格局展望

1. **PyTorch**仍将是研究和全栈开发的主流选择，其综合生态（HuggingFace、torch.compile、FSDP、TorchServe）提供了从研究到生产的最平滑路径。
2. **JAX**继续在需要极致TPU/GPU利用率和灵活组合的顶级研究场景（RL、大规模扩散模型、基础模型预训练）中保持领先地位。
3. **TensorFlow/Keras 3**通过多后端策略找到了差异化的生态位置——更注重"编写一次、任意后端部署"的标准化。
4. **Mojo**处于"早期展望期"——理论价值巨大但实际生态有待积累，其进展将决定未来10年AI框架的架构形态。
5. **MLX**将巩固Apple生态内本地AI计算的统治地位。

框架的最终演化目标是**硬件-编译-运行时的全栈融合**：用户用高层次的Python（或Mojo）编写逻辑，框架/编译器统一降级到MLIR多层IR，根据目标硬件自动选择最优的后端代码生成策略，在运行时通过统一的推理引擎（ONNX Runtime / TensorRT / CoreML）执行。这一愿景的实现仍需要时间，但2026年时其轮廓已经清晰可见——框架之争正在从"谁的API好用"转向"谁的编译器更智能、谁的硬件适配更广"。
