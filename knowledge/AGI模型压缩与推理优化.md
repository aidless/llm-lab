# AGI 模型压缩与推理优化

---

## 总览：让大模型跑得动、跑得快

训练一个千亿模型需要万卡——但**部署**它只需要"让每 token 的成本降下来"。模型压缩（量化、剪枝、蒸馏）解决"模型太大"——推理优化（KV Cache、FlashAttention、投机解码、continuous batching）解决"服务太慢"。两者合起来——是把"研究原型"变成"可盈利产品"的工程主干。vLLM、TensorRT-LLM、llama.cpp 的成功——证明了"推理即产品"。对 AGI 而言——推理成本直接决定"每个用户能用多少思考预算"——**推理优化的上限——就是智能民主化的上限**。

```
训练好的权重 ──→ 压缩（瘦身）
                    ├── 量化: FP16 → INT8/INT4（GPTQ/AWQ/SmoothQuant）
                    ├── 剪枝: 结构化 / 非结构化（SparseGPT/Wanda）
                    └── 蒸馏: 大模型教小模型（MiniLM/KL 蒸馏）
                            │
                            ▼
推理引擎（加速）
 ├── FlashAttention 1/2/3（注意力算法层）
 ├── KV Cache 管理（PagedAttention/vLLM、GQA、量化 KV）
 ├── 调度（continuous batching、prefix caching、chunked prefill）
 └── 投机解码（draft model / Medusa / EAGLE）
                            │
                            ▼
目标: 更低延迟 × 更高吞吐 × 更低成本 × 更省显存
```

## 一、量化：把数字变"瘦"

### 1.1 量化基本原理

**量化**——把高精度数值（FP16/BF16/FP32）映射到低精度整数（INT8/INT4）——减少存储与计算。

**均匀量化**（uniform quantization）——最常用：

**核心公式**：
```
r = s · (q - z)        （反量化）
q = round(r / s) + z   （量化）
s = (r_max - r_min) / (q_max - q_min)   （缩放因子 scale）
z = q_min - round(r_min / s)            （零点 zero-point）
```

- **对称 vs 非对称**：对称（z=0）简单——适合权重；非对称多一个零点——适合激活（ReLU 后非负）
- **逐张量 vs 逐通道（per-channel）**：权重按输出通道各给一个 scale——精度大幅提升——现代 LLM 量化的标配
- **粒度**：group 量化（GPTQ 等）——把通道分成 group（如 128）——每 group 一个 scale——平衡精度与开销

**为什么要 INT 量化**：
- 显存减半/减 4 倍（FP16→INT8→INT4）
- 整数运算的 TFLOPs 是浮点的 2~4 倍（Tensor Core INT8 支持）
- 内存带宽瓶颈场景（自回归解码）——位宽减半→带宽减半→**延迟直接减半**

### 1.2 PTQ（训练后量化）与 QAT（量化感知训练）

| 方法 | 流程 | 精度 | 成本 |
|------|------|------|------|
| PTQ | 训练完直接量化 | 中-高 | 极低（几小时） |
| QAT | 训练时模拟量化 | 高 | 高（重训练） |

- **QAT**：前向用"伪量化"（fake quant）——STE（Straight-Through Estimator）把量化阶梯的梯度近似为直通——让网络学会"对量化鲁棒"
- LLM 规模下 QAT 昂贵——主流是 **PTQ + 校准（calibration）**：用少量数据（128~512 条）观察激活分布——确定 scale

### 1.3 大模型 PTQ 的三个里程碑

**LLM.int8()（2022）**：
- 发现：激活的**离群特征**（outlier）集中于少数维度——幅值远超正常值
- 方案：大部分矩阵 INT8 计算 + 离群维度单独 FP16 计算（混合分解）
- 结论：不降精度的 8-bit 推理成为可能

**GPTQ（2022）**——目前 INT4 的事实标准：
- 逐层、逐列地**最小化量化误差的二次形式**：

```
min  || W X - Ŵ X ||²₂     （W 真实权重，Ŵ 量化权重，X 校准输入）
```

- 用**二阶 Hessian 信息**（H = X Xᵀ）做"最优更新"——量化当前列后——用误差对"尚未量化的列"做补偿更新（类似 LDL 分解/Cholesky 的递归）
- 一次性量化（不需要反传）——GPTQ 甚至可以在量化时继续校准——1B~65B 模型直接 4-bit 部署（group size 128）

**AWQ（2023）**——激活感知量化：
- 观察：权重的重要性由**激活幅值**决定——而非权重幅值
- 方案：不量化那 ~1% 的"显著通道"（保持 FP16）——**对非显著通道的权重做缩放（scaling）**——让量化误差集中在不重要处
- 比 GPTQ 快 20× 的量化速度——精度相当甚至更好——离线转换、无需重训练

**SmoothQuant（2022）**——把激活离群"搬"到权重：
- 问题：激活离群让 W8A8 量化失败（激活难以量化）
- 思想：**数学恒等变换**——把激活的难量化性"迁移"给好量化的权重：

```
Y = X·W = (X·diag(s)) · (diag(s)⁻¹·W)
s_j = max|X_j|^α / max|W_j|^(1-α)   （α 平滑系数，常取 0.5）
```

- 效果：**W8A8 全整数推理**——激活与权重都可 8-bit——配合 TensorRT-LLM 等达到接近 FP16 的精度
- 意义：FP8/INT8 硬件利用率（Hopper 的 FP8 算力是 FP16 的 2 倍）被真正解锁

### 1.4 更多量化格式与前沿

- **NF4（NormalFloat4）**：QLoRA 提出的 4-bit 格式——按正态分布分位点分布数值——信息论最优
- **FP8（E4M3/E5M2）**：H100 原生支持——训练+推理双用——scaled FP8 训练成为万亿级标配
- **MXFP（Microscaling）**：块级共享 scale——硬件友好
- **K-means 量化**：按簇心映射（老方法——Deep Compression）
- **GGUF + Q4_K_M 等**：llama.cpp 生态的分级量化（Q2~Q8 + 混合）——消费级 CPU/GPU 部署的标准
- 趋势：**量化与训练一体化**（训练时就考虑部署格式）——以及"量化+稀疏+蒸馏"的组合压缩

## 二、剪枝：把权重变"少"

### 2.1 非结构化剪枝

- **幅度剪枝（magnitude pruning）**：把绝对值最小的权重置零——简单但朴素
- **SparseGPT（2023）**：把 GPTQ 的"最优补偿"思路用于剪枝——不需要重训练即可剪到 50-70% 稀疏且保持困惑度
- **Wanda（2023）**：权重幅值 × 激活幅值——作为重要性分数——零训练、零校准——与 SparseGPT 相当

```
Wanda 分数: S_j = |W_j| · ||X_j||₂   （按输入特征范数加权）
剪掉 S 最小的比例
```

**问题**：非结构化稀疏需要稀疏 kernel 支持才能实际加速（A100 的 2:4 稀疏是特例）——软件生态不成熟——所以"研究热、部署冷"。

### 2.2 结构化剪枝

- 剪掉**整行/整通道/整个注意力头**——保持稠密张量——通用 kernel 直接加速
- 对象：注意力头（head pruning）、FFN 中间维、嵌入维、MoE 专家数
- 挑战：LLM 权重高度耦合——结构剪枝损失显著——常需要 **short fine-tune 恢复**
- 实例：剪 25% 注意力头 + 20% FFN——困惑度损失 <1%——可配合 LoRA 快速恢复

### 2.3 稀疏格式与硬件

- **2:4 结构化稀疏**（A100/H100 原生）：每 4 个元素保留 2 个——Tensor Core 直接 2× 加速
- **动态稀疏 vs 静态稀疏**：LLM 激活的动态稀疏（ReLU 族）研究仍在早期
- **蒸馏与剪枝结合**：剪枝提供结构——蒸馏恢复精度——常见于移动端小模型

## 三、知识蒸馏：大模型教小模型

### 3.1 Hinton 蒸馏框架

**软标签**（soft targets）——大模型（teacher）输出的概率分布比独热标签包含更多信息：

**核心公式**：
```
L = (1-α)·L_CE(y, σ(z_student)) + α·T² · KL( σ(z_teacher/T), σ(z_student/T) )

σ(z/T)_i = exp(z_i/T) / Σ_j exp(z_j/T)     （温度 T 软化分布）
```

- T > 1：分布更"平"——暗知识（类别间相对关系）被保留
- T² 乘回 KL——平衡梯度尺度
- 意义：小模型学到的不只是答案——还有大模型的"思维方式"（类别相似性）

### 3.2 LLM 时代的蒸馏

**DistilBERT / DistilGPT-2**：学生 = 教师的一半层——KD + 教师隐藏状态监督（MSE 对齐）——保留 95%+ 能力——体积减半

**MiniLM（2021）**——深度自注意力蒸馏的 SOTA 通用方法：
- 关键：蒸馏**自注意力**（QK 点积矩阵）而非隐藏状态——更通用
- 目标：让学生每层的注意力矩阵逼近教师**最后一层**的注意力（+ scaled 版本加值矩阵 V）：

```
L_SA = Σ || S^s - S^t ||²    （S = softmax(QKᵀ/√d)）
```

- MiniLMv2：蒸馏**关系向量**（head 间关系）——进一步超越
- 用途：语义向量模型（Embedding 模型）的标准蒸馏范式——sentence-transformers 生态大量采用

### 3.3 蒸馏的新形态

- **数据蒸馏**：用教师生成训练数据（生成式蒸馏）——LLM 时代的主流（如 SFT 数据蒸馏）
- **CRD（对比蒸馏）**：正负样本对的关系蒸馏
- **在线蒸馏/自蒸馏**：学生同时训练——互相学习
- **MoE 蒸馏**：把大 MoE 蒸成稠密模型（DeepSeek 系列的把戏）
- **蒸馏 + RL**：RLHF 后的教师蒸馏给学生——减少对齐成本
- 教训：蒸馏天花板 = 教师——学生容量不足时精度暴跌——"蒸馏不是白嫖"

## 四、KV Cache：自回归解码的命脉

### 4.1 为什么需要 KV Cache

自回归生成时——每个新 token 都要对**所有历史 token** 做注意力。若不缓存——每次重算所有 Key/Value——复杂度 O(n²)。

**KV Cache 含义**：把历史 token 的 K、V 矩阵缓存下来——新 token 只算自己的 Q 与 K/V——复杂度降为 O(n)。

**显存占用**（关键公式）：
```
每 token 每层的 KV 大小 = 2（K和V）× 层数 L × 头数 H × 每头维度 d
例: 70B 模型（L=80, H=64, d=128）→ 每 token ≈ 1.3MB
    4K 上下文 → ~5.3GB；128K 上下文 → ~170GB（远超模型本身）
```

KV Cache 的膨胀——是长上下文与高并发的**第一瓶颈**——催生了整整一代优化技术。

### 4.2 PagedAttention 与 vLLM

**问题**：传统推理把 KV 按"连续大块"预留——提前按最大长度分配——导致：
- 内部碎片：请求短却预留长
- 外部碎片：不同请求的连续块无法共享
- 利用率常只有 20-40%

**PagedAttention（vLLM, 2022/2023）**——把操作系统的**分页/虚拟内存**思想引入 KV：
- KV 按固定大小**块**（block）管理——块可映射到不连续的物理内存
- 每请求维护块表（block table）——逻辑连续、物理任意
- **写时复制（COW）**：多请求共享同一前缀的 KV（beam search、并行采样）
- 效果：内存利用率逼近 100%——吞吐提升 2-4×——vLLM 由此成为开源推理的事实标准

```
请求 A: [块5][块9][块3]  ← 逻辑连续，物理分散
请求 B: [块5][块9][块7]  ← 与前缀共享块（COW）
```

### 4.3 GQA/MQA：减少 KV 的架构级方案

**MHA**（多头注意力）：每头独立 K/V——KV 最大
**MQA**（多查询）：所有头共享一组 K/V——KV 减为 1/H——质量略降
**GQA**（分组查询，2023）：H 个头分成 G 组——组内共享 K/V——折中

```
MHA:  H 组 KV      GQA:  G 组 KV      MQA:  1 组 KV
```

- 推理速度提升 2~3×（内存带宽瓶颈下）——训练质量几乎无损
- **LLaMA 2/3、Mixtral、Qwen 等 2023 后主流模型全部标配 GQA**（如 32 头分 8 组）

### 4.4 KV Cache 量化与淘汰

**量化 KV**：
- 每层每头独立 scale（per-head/per-token dynamic quant）
- INT8 KV：精度基本无损（结合 SmoothQuant 思想）
- FP8 / INT4 KV + 调优：长上下文下的显存减半~减四分之三
- 量化 KV 是"带宽×2~4"的免费午餐——推理引擎（vLLM/TensorRT-LLM）已内建

**KV 淘汰（eviction）**——显存不够时的降级方案：
- **H2O（Heavy-Hitter Oracle）**：只留注意力分数高的"重头 token"
- **StreamingLLM**：保留开头几个 token（注意力汇聚点）+ 最近的窗口——无限上下文变体
- **Retention / 滑动窗口**：架构级——只对近窗口算注意力
- 代价：淘汰是有损的——长距离依赖会被截断——工程上常作为兜底而非首选

### 4.5 Prefix Caching（前缀缓存）

- 系统提示词、few-shot 示例、工具定义——每次请求重复计算
- **Radix Tree 前缀树缓存**：按公共前缀分叉——共享 KV 块——命中则直接续算
- vLLM 的 `--enable-prefix-caching`、SGLang 的 RadixAttention——多轮对话与 agent 场景吞吐提升 3-10×

## 五、FlashAttention：把注意力算法"算子化"

### 5.1 动机：注意力是内存密集型

自注意力计算是"访存密集"（memory-bound）的：

```
QKᵀ (n×n 矩阵) 需要写回 HBM 再读回来 —— 中间矩阵的读写量 O(n²) 是瓶颈
```

FlashAttention 的核心目标——**不把注意力矩阵写进全局显存（HBM）**。

### 5.2 FlashAttention-1（2022）

- **分块（tiling）**：把 Q、K、V 切成块——在 **SRAM（片上缓存，~20MB）** 内逐块计算
- **Online Softmax 算法**：softmax 的归一化因子（统计量 m, l）在遍历块时**增量更新**——不必等全部分数算完

```
分块伪代码:
for Q_j 块:
    m = -∞; l = 0; acc = 0
    for K_i, V_i 块:
        分数 S_ij = Q_j K_iᵀ / √d
        m_new = max(m, rowmax(S_ij))
        用 m_new 修正 l 与 acc（rescaling）
    O_j = acc / l
```

- 理论加速：HBM 读写从 O(n²) 降到 O(n²·d/SRAM 容量) ——实际 2-4× 加速——并且**显存与序列长度线性**——长序列不再是噩梦
- 首个"IO-aware"（I/O 复杂度分析）的注意力实现

### 5.3 FlashAttention-2（2023）

- **并行性改进**：把序列维度（Q 块）设为并行线程/块索引——而非 batch×head 上并行（block 数不足时利用率高）
- **减少非矩阵乘操作**：rescale 与 softmax 统计的标量操作最少化——不再存中间 l 统计量到寄存器
- 效果：**2-3× 于 FA1**——达到 GPU 理论峰值 50-70%（A100）——H100 上配合 FP8 更高
- 生态：PyTorch `scaled_dot_product_attention`（SDPA）、xFormers、cuDNN 均已内置 FA2 思想

### 5.4 FlashAttention-3（2024，Hopper 专属）

利用 H100 的新硬件特性：
- **Warp 特化（warp specialization）**：生产者-消费者结构——一组 warp 做矩阵乘（MMA）——另一组做 softmax/rescale（非 MMA）——流水线并行
- **TMA（Tensor Memory Accelerator）**：异步、多维度复制——把 SRAM-HBM 搬运交给硬件单元——计算不被搬运阻塞
- **异步流水线**：把 TMA 加载、SRAM 计算、结果写回三阶段重叠——且支持 FP8 累加
- 效果：相对 FA2 再快 ~1.5-2×——接近 H100 理论峰值
- 其他竞争者：cuDNN Flash Attention、Flashattention-3 的变体、以及融合进 MLA（DeepSeek 多头潜注意力）的优化

### 5.5 注意力家族的其他优化

- **GQA + FlashAttention**：组合使用——KV 减载 + 分块
- **MLA（Multi-head Latent Attention）**：把 K/V 压缩成低秩潜向量——KV 再降 ~90%——DeepSeek-V2 起标配——推理成本骤降
- **线性注意力（Mamba/RetNet 族）**：O(n) 复杂度——KV 消失——以质量换速度的路线
- 未来：**推理时注意力**（如状态化注意力、硬件感知自动调度）

## 六、推理引擎：把优化装进产品

### 6.1 vLLM：开源事实标准

核心组件：
- **PagedAttention**（见 4.2）
- **Continuous Batching（连续批处理）**：不再等"整批完成"——**一个请求结束立即腾出位置给新请求**——GPU 利用率大幅提升
- **Chunked Prefill**：把长 prompt 的预填充切成块——与生成阶段（decode）混合调度——避免"预填充长 prompt 时其他请求饿死"
- **投机解码集成**：原生支持 draft model 与 Medusa（见 6.4）
- **量化支持**：GPTQ/AWQ/FP8/SmoothQuant 一行开关
- 生态位：吞吐优先的在线服务、离线批量推理

### 6.2 TensorRT-LLM（NVIDIA）

- **In-Flight Batching（飞行中批处理）**：同 continuous batching——但深度绑定 TensorRT 编译与 CUDA 图
- **量化原生**：FP8/INT4 的 kernel 级优化——W8A8 配合 SmoothQuant
- **Attention 插件**：FlashAttention、XQA（上下文与生成解耦的 attention）等
- **多 GPU 推理**：TP/PP 的推理版——单请求拆到多卡
- 定位：**延迟最低、吞吐最高**——适合生产级 NVIDIA 集群——与 Triton Inference Server 集成
- 代价：编译时间长、生态较封闭——被 vLLM 的灵活性挑战

### 6.3 调度与内存管理（引擎共同内功）

- **显存池**：把空闲显存按块池化管理（vLLM block manager）——预分配避免碎片
- **请求排队与优先级**：FCFS + 长请求切块 + 抢占（preemption 时把 KV 换出到 CPU）
- **吞吐-延迟权衡**：max_num_seqs、max_batch_tokens 调参——延迟敏感的对话 vs 吞吐敏感的批处理
- **模型并行推理**：单卡放不下时 TP 推理（同训练——通信成为瓶颈）——70B 通常 2-4 卡 TP
- **量化与服务联动**：量化在**加载时**完成（加载-量化-服务一体）——GPTQ/AWQ 模型文件直接读

### 6.4 投机解码（Speculative Decoding）

**观察**：自回归逐 token 生成——每一步都是带宽瓶颈的小矩阵乘——GPU 算力大量空闲。

**思想**：用一个**廉价草稿模型（draft）**先"猜"出 k 个 token——再用大模型**一次并行验证**——正确则一次获得 k 个 token 的收益。

```
草稿模型:  a₁ a₂ a₃ a₄ （猜测，快）
大模型:    并行打分全部 4 个位置
接受率 α 个 → 输出 α 个 token —— 只回退到第一个错的
```

**验收与采样一致性**（保证与原始分布**完全一致**的采样方案）：
```
对每个草稿 token x：
  p = 大模型概率, q = 草稿概率
  以 min(1, p/q) 概率接受
  拒绝时: 从修正分布 norm(max(0, p-q)) 重新采样
```

- **接受率**：草稿质量决定——同族小模型（同 tokenizer）通常 0.6~0.9
- 变体：**Medusa**（大模型自己的解码头并行猜）、**EAGLE**（用倒数第二层特征做草稿）、n-gram 草稿（零额外模型）、**自投机**（拆分大模型浅层做草稿）
- 效果：**延迟降低 2-3×**——无精度损失——已全面进入 vLLM/TensorRT-LLM/llama.cpp
- 注意：**批量场景收益递减**（batch 大时 GPU 已忙）——主要优化单请求延迟与长序列

### 6.5 其他引擎与端侧路线

- **llama.cpp + GGUF**：CPU/消费级 GPU 推理——量化生态最全（Q4_K_M 等）——手机/笔记本可跑
- **MLC-LLM / ONNX Runtime**：跨平台编译——WebGPU 端侧
- **SGLang**：RadixAttention 前缀缓存 + 结构化控制流——agent/多轮场景吞吐领先
- **TGI（HuggingFace）**：老牌服务框架——生态集成好
- **DeepSeek 等厂的 MLA 优化**：推理成本对标 GPT-4 级服务的 1/20——把架构级优化推到极致
- 端侧趋势：**NPU/手机芯片上的量化小模型（3B~8B）+ 云边协同**——端侧推理是 AGI 落地的"最后一公里"

### 6.6 推理优化的完整决策树

```
场景: 延迟敏感（聊天/agent）→ 投机解码 + 前缀缓存 + 大 batch 上限低
场景: 吞吐优先（批处理/离线）→ continuous batching + chunked prefill + 大 batch
场景: 显存受限（长上下文）  → GQA 架构 + 量化 KV + 分页 KV + 淘汰兜底
场景: 成本受限（规模部署）  → INT4 量化 + 蒸馏小模型 + 投机草稿自蒸馏
场景: 端侧（手机/边缘）     → GGUF Q4 + 小模型蒸馏 + NPU 算子适配
```

## 七、推理的经济学与系统设计

### 7.1 推理成本模型

**核心指标**（服务商内部语言）：
```
成本 = 单价（$/M tokens） = 硬件摊销 + 电费 + 人力 / 总吞吐
吞吐（tokens/s） = 总带宽 × 利用率（decode 阶段 ≈ 显存带宽 × 参数位宽利用率）
延迟预算: 首 token 延迟（TTFT）< 1s，每 token 间隔（ITL）< 50ms（对话场景）
```

- **decode 是带宽瓶颈**：每 token 要"读完整个模型"——参数位宽直接决定速度（INT4 比 FP16 快 4×）
- **prefill 是计算瓶颈**：长 prompt 的并行矩阵乘吃满 GPU 算力
- 一句话：**模型的"内存占位"决定了它的服务成本**——压缩的每一 bit 都是钱

### 7.2 服务化架构

```
客户端 ──→ 网关（限流/鉴权/路由）──→ 推理集群（vLLM/TensorRT-LLM）
                    │                      │
                    ├── 多模型路由（模型 A/B 分流）  ├── 弹性扩缩（K8s）
                    └── 缓存层（提示词/回答缓存）    └── 监控（延迟/成本/错误率）
```

- **多租户隔离**：按客户隔离（SLA 不同）——vLLM 的命名空间与配额
- **冷热分层**：热门模型常驻 GPU——冷门模型按需加载（秒级 swap）
- **批处理 API**：离线任务用大 batch + 低优先级队列——在线任务小 batch 高优先级
- **回退策略**：超时 → 降级到小模型/缓存回答——SLA 兜底

### 7.3 推理集群的资源调度

- **KV 显存与模型显存的分配比例**：模型 60% / KV 40%——比例随并发调节
- **多模型共卡**：显存分片隔离（MIG / 显存配额）——GPU 利用率提升的关键
- **异构调度**：小请求 → 小模型/共享卡；大请求 → 专卡
- **量化与精度分层**：同一模型部署 FP8（质量高）/ INT4（便宜）两档——按客户等级路由
- **推理与训练共池**：夜间训练、白天推理（训练-推理错峰）——芯片利用率最大化

### 7.4 推理服务的质量保障

- **延迟 SLO 监控**：P50/P95/P99 延迟、TTFT、ITL 分布——超限自动扩容
- **吞吐-质量权衡仪表盘**：batch size、并发数、KV 淘汰率与质量分同屏展示
- **A/B 评估**：模型更新（量化/蒸馏）上线前——与旧版本跑同流量对比（质量+延迟双指标）
- **优雅降级**：峰值流量 → 动态降 batch、启用投机解码降延迟、拒绝长上下文请求
- **成本报表**：每客户、每模型的 tokens/成本归因——驱动压缩投入的 ROI 计算

## 八、端侧与边缘推理

### 8.1 为什么端侧

- **隐私**：数据不出设备（医疗、金融、个人助理）
- **延迟**：无网络往返——本地推理 < 100ms
- **成本**：云推理单价 × 亿级设备 = 天文数字——端侧一次付费
- 趋势：**混合架构**——简单任务端侧、复杂任务云端（设备侧路由）

### 8.2 端侧部署栈

```
模型:  3B~14B 量化模型（Qwen2.5-3B/7B、Llama-3-8B、Gemma）
格式:  GGUF（llama.cpp）/ MLX（Apple）/ ONNX（Windows/NPU）
硬件:  手机 NPU（骁龙/天玑/A 系列）、笔记本 NPU（Intel/AMD）、机器人边缘盒子
栈:    llama.cpp、MLC-LLM、ExecuTorch（PyTorch 官方边缘运行时）
```

- **内存带宽是端侧最大瓶颈**：手机 LPDDR5X ~60GB/s——14B INT4 ≈ 8GB 权重——生成 20 tokens/s 是上限
- **NPU 适配**：算子需要映射到 NPU 指令（Transformer 的算子集有限——GQA、RoPE、量化 matmul 是核心）
- **系统集成**：显存预算共享（NPU 与 GPU 同池）、功耗约束（<5W）、发热控制

### 8.3 端侧质量与云端协同

- **端侧小模型 + 云端大模型蒸馏**：云端教师 → 端侧学生（同 tokenizer 便于切换）
- **设备上自适应**：个人数据在端侧微调（LoRA）——个性化且隐私
- **离线能力**：飞行模式可用（翻译、文档、助手）
- 评测：端侧专属基准（延迟、功耗、内存占用、质量平衡）——与云端评测标准不同

## 十、部署实战：引擎选型与调优

### 10.1 引擎对比：没有银弹

| 引擎 | 核心优势 | 适合场景 | 备注 |
|------|----------|----------|------|
| vLLM | PagedAttention、生态最大 | 通用服务、快速上线 | OpenAI 兼容 API |
| TensorRT-LLM | 极致性能（kernel 级） | 大规模生产、吞吐优先 | 编译时间长、算子受限 |
| SGLang | RadixAttention、多模态 | 复杂提示工程、多模态 | 前缀复用极强 |
| llama.cpp | CPU/边缘都能跑 | 端侧、个人部署 | GGUF 生态 |
| MLX | Apple Silicon 优化 | Mac 本地推理 | 内存统一架构友好 |

**选型逻辑**：延迟敏感 → TensorRT-LLM/SGLang；吞吐优先 → vLLM；端侧 → llama.cpp/MLX；**新特性（Mamba 等）→ vLLM 跟得最快**。

### 10.2 典型部署参数（数值示例）

```
示例: Llama-3-70B，INT4（AWQ），2× A100-80G 或 1× H100-200G
显存分解: 权重 ~35GB（70B×0.5B） + KV 缓存（8K 上下文 × 128 并发 ≈ 24GB） + 激活余量
吞吐参考: 单卡 100-300 tokens/s（batch 32-128，continuous batching）
首 token 延迟: prefill 1K token 提示 ≈ 200-500ms（视 batch 大小）
```

- **KV 配额是服务商的核心调优旋钮**：KV 显存占比 20%-50%——太高排队掉并发，太低每请求变慢
- **批量与延迟的帕累托**：延迟预算 2s 时 batch 可拉到多大？——压测曲线决定
- **量化与精度分层**：同一模型 FP8/INT4 两档部署——高价值客户走 FP8、低成本通道走 INT4

### 10.3 常见问题排查手册

- **OOM**：显存不足 → 降 batch、降 KV 配额、启用 KV 淘汰、升级量化位宽
- **延迟抖动**：长尾请求（长 prefill）挤占 decode → 分优先级队列 + 限制单请求 max_tokens
- **质量突然下降**：KV 淘汰过狠 / 量化掉点 → 回退配置、跑回归评测
- **吞吐上不去**：看 GPU 利用率——如果是带宽瓶颈（decode）→ 换低位宽；如果是算力瓶颈（prefill）→ 换大 batch
- **前缀缓存命中率低**：prompt 前缀不稳定 → 固定 system prompt 模板——RadixAttention 命中率可到 80%+
- 方法论：**一切改动都先压测再上线**——配置变更 = 回归测试（质量 + 延迟 + 成本三表）
- **上线清单**：压测报告 → 质量回归 → 灰度（5% 流量）→ 对比监控（旧版基线）→ 全量——推理系统的改动同样需要"发布流程"

## 十一、总结

```
精度优先 ←───────────────────→ 速度优先
FP16 ─→ INT8/FP8 ─→ INT4 ─→ NF4/混合量化
稠密 ─→ 2:4 稀疏 ─→ 结构化剪枝 ─→ 蒸馏小模型
MHA ─→ GQA ─→ MLA/线性注意力
朴素注意力 ─→ FlashAttention ─→ FA3/融合 kernel
静态批处理 ─→ continuous batching ─→ 投机解码 + 前缀缓存
```

**工程铁律**：
1. **先测瓶颈再优化**——是带宽瓶颈（decode）还是计算瓶颈（prefill）——手段完全不同
2. **压缩与推理联动**——量化决定 kernel——架构（GQA/MLA）决定 KV——一起设计才最优
3. **质量回归测试**——每次压缩/加速都必须跑标准集（PPL、MMLU、任务集）——防止"静默降智"
4. **无免费午餐**——量化掉点、投机复杂化、淘汰有损——收益与风险用 SLO 度量

对 AGI 的意义：**"思考预算"是新的算力商品**——o1/R1 时代的推理时缩放（test-time scaling）让推理量爆炸式增长——推理引擎的每一倍吞吐提升——都直接转化为"每个用户多几秒思考"或"同样的钱多训练一轮 RL"。压缩与推理优化——从"工程细节"升格为"AGI 的经济基础"。
