# AGI 分布式训练

---

## 总览：把万亿参数搬上万卡

现代 AGI 模型——动辄数千亿到数万亿参数——单卡显存（H100 80GB）连"参数+梯度+优化器状态"都放不下。分布式训练——本质上是三件事：**把数据分给谁算、把模型分给谁存、把梯度如何通信**。数据并行（DP/DDP）、张量并行（TP）、流水线并行（PP）、ZeRO、序列并行、混合并行（3D/4D）——构成了从"一张卡训小模型"到"万卡训万亿模型"的完整光谱。Megatron-Turing 530B、GPT-3 175B、DeepSeek 系列——都是这套组合拳的实战案例。

```
数据 ──→ 数据并行（每个 GPU 一份模型，各算各的梯度）
              │
              ▼
      AllReduce（ring-allreduce 聚合梯度）
              │
模型太大 ──→ 张量并行（一层切到多卡）
              │
              ▼
      流水线并行（层分多段，1F1B 填气泡）
              │
              ▼
      混合并行（TP × PP × DP = 3D；+ CP = 4D）
              │
              ▼
      ZeRO（优化器/梯度/参数分片 + Offload 到 CPU/NVMe）
              │
              ▼
      通信优化（梯度压缩、通信计算 overlap、all2all）
              │
              ▼
      实践：checkpoint / 故障恢复 / 集群调度
```

## 一、数据并行：DP 与 DDP

### 1.1 基本思想

每个 worker（GPU）持有**完整的模型副本**——把训练数据切成 N 份——各自前向反向——再**聚合梯度**更新：

```
GPU0: 数据分片0 ──→ 前向/反向 ──→ g₀ ──┐
GPU1: 数据分片1 ──→ 前向/反向 ──→ g₁ ──┼── AllReduce ──→ ḡ = (g₀+g₁+...+gₙ)/N
GPU2: 数据分片2 ──→ 前向/反向 ──→ g₂ ──┤                    │
...                                   │                    ▼
                                         所有卡用 ḡ 更新各自副本（保持参数一致）
```

### 1.2 DP 与 DDP 的区别（PyTorch）

| 特性 | DP（DataParallel） | DDP（DistributedDataParallel） |
|------|--------------------|--------------------------------|
| 实现 | 单进程多线程 | 多进程（每卡一进程） |
| 通信 | 单卡 PS 模式收集再广播 | AllReduce（每梯度一次） |
| 性能 | GIL 瓶颈、主卡负载重 | 通信与计算 overlap |
| 推荐 | 不再推荐 | **事实标准** |

### 1.3 梯度 AllReduce 与 Ring-AllReduce

**AllReduce**——把分布在各卡的向量"归约（求和/平均）并广播"给所有人。

**Ring-AllReduce**（最常用的带宽最优算法）——每个节点只与相邻节点通信——把 N 卡环状组织：

```
阶段1（reduce-scatter）: 梯度切 N 块，每块沿环"转发求和"——N-1 步
阶段2（all-gather）:    每卡持有"部分和"——沿环传播完整结果——N-1 步
总通信量 = 2·(N-1)/N · 数据量  （接近 2× 数据量——与 N 无关）
```

**带宽分析**（关键结论）：
- 朴素 PS（主从参数服务器）总带宽 = 2(N-1)·数据量——随 N 线性增长
- Ring-AllReduce 总带宽 ≈ 2·数据量——与节点数无关——**大规模下必然胜出**
- 工程实现：NCCL（NVIDIA Collective Communications Library）——Ring、Tree、NvLink 拓扑感知

### 1.4 DDP 的关键工程细节

- **通信计算 overlap**：梯度算完一块就发一块（bucket 机制，默认 25MB）——反向与通信并行
- **同步更新**：DDP 是同步的（所有卡一个 global batch）——保证一致性
- **梯度平均**：默认"sum 再除 world_size"——注意 loss 已经是 per-batch 平均时不要重复除
- **混合精度注意**：fp16 梯度反传后——AllReduce 用 fp32 累积避免溢出
- **batch size 缩放**：全局 batch = 单卡 batch × world_size——学习率/热身需相应调整（线性缩放法则）

## 二、模型并行：张量并行（TP）

### 2.1 动机

模型太大——单卡存不下**一个权重矩阵**。张量并行（Tensor Parallelism, TP）——把**单个算子的矩阵**切成多卡——各卡算一部分——再合并。Megatron-LM（NVIDIA）的 1D 切分是标准做法。

### 2.2 Megatron 的列并行与行并行

对线性层 Y = X·W：

**列并行（Column Parallel）**——把 W 按列切：

```
W = [W₁ | W₂]（列切）
Y = X·[W₁ W₂] = [X·W₁, X·W₂]
每卡: Yᵢ = X·Wᵢ（输入 X 需要广播，输出 Y 拼接）
```

**行并行（Row Parallel）**——把 W 按行切：

```
W = [W₁; W₂]（行切）
Y = X·W = X₁·W₁ + X₂·W₂
每卡: 各算 Xᵢ·Wᵢ，再 AllReduce 求和
```

### 2.3 Transformer 中的 TP 布局（Megatron）

```
Attention 块:
  QKV 投影 ──→ 列并行（3 组并排切）
  attention 输出投影 ──→ 行并行
MLP 块:
  gate/up 投影 ──→ 列并行
  down 投影 ──→ 行并行
Dropout/残差前 ──→ 先 AllReduce 恢复全量
```

- **f / g 标识函数**：Megatron 在切分边界插入 f（前向恒等/反向 AllReduce）与 g（前向 AllReduce/反向恒等）——把"何时通信"形式化
- **每层通信次数**：Attention 输出投影后 1 次 AllReduce + MLP 输出后 1 次 AllReduce——每层 2 次——与层数无关的常数开销占比
- 优点：计算完全均衡、通信量小（每层仅 O(seq×dim) 量级）
- 缺点：**TP 需要 N 卡在同一个节点**（NvLink 高速互联）——跨节点 TP 太慢——所以 TP 度受节点内卡数限制（典型 8）

### 2.4 2D/2.5D 张量并行（后续发展）

- 2D TP（SUMMA 类）：行列都切——通信复杂度 O(√N)——用于更大规模
- MoE 的 expert 并行本质上是"扩展的列并行"——all-to-all 通信（见第七章）

## 三、流水线并行：PP

### 3.1 基本思想

把模型按层切成 P 段（stage）——每段放一块 GPU——数据像流水线一样流过。**切层不切算子**——比 TP 通信少得多（只传激活）——但引入"气泡"（bubble）。

### 3.2 Naive 流水线与 GPipe

**Naive**：一个 micro-batch 只能在一段上算——同一时刻只有一段在干活——利用率 1/P——不可用。

**GPipe**：把 batch 切成 M 个 micro-batch——每个 stage 算完 micro-batch i 就传给下一 stage——重叠执行：

```
stage 1: [b1][b2][b3][b4]       （前向）
stage 2:     [b1][b2][b3][b4]
stage 3:         [b1][b2][b3][b4]
         ↑ 气泡（bubble）区域
```

**气泡率**（关键公式）：
```
bubble 占比 = (P - 1) / (M + P - 1)   ≈ (P-1)/M（M 大时）
```

- P=4, M=32 → 气泡 ≈ 9%——可以接受
- 代价：**每张卡要缓存 M 份激活**用于反向传播——显存压力大

### 3.3 1F1B（one-forward-one-backward，交错调度）

**1F1B**（Megatron 论文的 interleaved schedule）——前向与反向**交替执行**——比 GPipe 少 1/3 激活缓存——并降低气泡：

```
stage 1: F1 F2  B1 F3  B2  B3 ...
stage 2:    F1 F2  B1 F3  B2 ...
```

**交错流水线（interleaved pipeline）**——每张卡放**多个**"虚拟 stage"——气泡进一步下降：

```
把 P=4 切 8 份，每卡 2 份:
bubble ≈ (P-1)/(M·V + P - 1)，V = 每卡虚拟段数
```

- V 翻倍——气泡几乎减半——但通信次数增加
- Megatron 默认组合：TP=8 × PP=8 时常用 V=2 的 interleaved 1F1B

### 3.4 流水线并行的其他流派

- **PipeDream**：1F1B 的前身——异步交错——显存最优——但梯度不一致
- **Chimera / V-Shape**：进一步优化气泡
- **零气泡调度（ZB, 2024）**：把部分反向计算并入气泡——理论气泡趋近 0
- **关键权衡**：PP 通信量小（每 micro-batch 一次点对点）——但难以负载均衡（层不均匀）——常与 TP 配合使用

## 四、混合并行：3D 与 4D

### 4.1 3D 并行：DP × TP × PP

```
                TP（组内切算子，NvLink）
   ┌─────────┬─────────┬─────────┐
   │ GPU0    │ GPU1    │ GPU2    │← PP 方向（切层，跨节点）
   │ 段0     │ 段1     │ 段2     │
   ├─────────┼─────────┼─────────┤
   │ GPU3    │ GPU4    │ GPU5    │← PP 方向
   │ 段0     │ 段1     │ 段2     │
   └─────────┴─────────┴─────────┘
        ↑ DP 方向（复制整条流水线）
```

**维度的分工**：
- **DP 维度**：复制模型——处理"数据多"
- **TP 维度**：切算子——处理"算子大"——必须高速互联
- **PP 维度**：切层——处理"模型深"——通信少——可跨节点

### 4.2 经典配置（实战案例）

**GPT-3 175B（8×A100 节点级）**：
```
175B = DP 64 × TP 8 × PP 8（近似），batch 1536，训练 3.5 个月
```

**Megatron-Turing NLG 530B（NVIDIA + Microsoft）**：
```
TP=8 × PP=35（56 个 stage 交错） × DP=4，共 2240 张 A100-80G
4 机架 × 4 节点 × 8 卡，NvLink + IB 混合互联
损失函数: 通信与计算 1:1 overlap——MFU ≈ 46.5%
```

**关键指标**：**MFU**（Model FLOPs Utilization）= 实际算力 / 理论峰值——530B 达到 ~46.5%——社区认为 50%+ 已属优秀。

### 4.3 4D 并行：加入序列/上下文并行

当序列长度进入 128K~1M——激活内存与注意力计算成为瓶颈——需要**上下文并行（Context Parallelism, CP）**：

```
4D = DP × TP × PP × CP
CP: 序列维度切成 C 段——每段算一部分注意力/MLP——跨段用 Ring 通信
```

- **Ring Attention**：把序列分段+注意力分块——块间 ring 传递——O(1) 激活显存
- **Ulysses 注意力**：Q/K/V 按序列切——all-to-all 通信——对 TP 友好
- **Megatron-SP（序列并行）**：LayerNorm/Dropout 的 token 维切分——消除激活冗余（见第六章）
- 长上下文训练（DeepSeek-V3 等）普遍用 DP×TP×PP×CP 四维组合

## 五、ZeRO：分片一切

### 5.1 动机与总览

数据并行"每人一份完整副本"——参数、梯度、优化器状态各存 N 份——**内存浪费 N 倍**。ZeRO（Zero Redundancy Optimizer, DeepSpeed）——把这些**分片**存储——需要时再收集。按分片粒度分 3 个 stage：

```
每个 GPU 保存的（N 卡，模型参数 Ψ）:
原始 DP: 参数 Ψ + 梯度 Ψ + 优化器状态（Adam: 12Ψ）≈ 14Ψ
Stage 1: 优化器状态分片 → 4Ψ + 14Ψ/N
Stage 2: 优化器状态 + 梯度分片 → 2Ψ + 14Ψ/N
Stage 3: 优化器状态 + 梯度 + 参数全部分片 → 14Ψ/N
```

（Adam 状态 = 参数 Ψ 的 12 倍：m、v、master weights 各 4Ψ 空间）

### 5.2 三个 Stage 的细节

**Stage 1（优化器状态分片）**：
- 每卡只更新自己的 1/N 参数——其余优化器状态不存在
- 通信量：与普通 DDP 相同（一次梯度 AllReduce）——**几乎零成本降内存**

**Stage 2（+ 梯度分片）**：
- 每卡只保留自己负责分片的梯度——其余梯度过手后即弃
- 通信量仍是 O(Ψ)——但内存再降 2Ψ/N

**Stage 3（+ 参数分片）**：
- 参数也不存全量——前向/反向用到哪块——从"拥有者"那里拉取（gather）——用完即释放（reduce-scatter）
- 通信量上升：每层前向一次 all-gather（拉参数）——反向一次 all-gather（再拉）+ reduce-scatter（归约梯度）——约 3 倍 DDP 通信
- **N=64 时**：14Ψ/N ≈ 0.22Ψ——500B 模型只需 ~20GB/卡——理论可训万亿级

### 5.3 ZeRO-Offload / ZeRO-Infinity

**ZeRO-Offload**——把**优化器状态和梯度**放到 CPU 内存（甚至参数）：

```
GPU: 前向/反向 + 参数
CPU: 优化器状态 + 梯度（Adam 更新在 CPU 完成）
每步通信: 梯度下传 + 更新后参数回传（各一次）
one-step-delay: 参数更新滞后一步——通信与计算完全 overlap
```

- 效果：单卡 24GB 可训 13B 模型（混合 4bit 甚至 30B+）——消费级显卡的福音

**ZeRO-Infinity**——把分片进一步卸载到 **NVMe SSD**：
- 带宽：NVMe（~7GB/s Gen4）比 CPU 内存带宽（~100GB/s）低一个量级
- 策略：**只卸载"冷"数据**（大模型参数、优化器状态）——"热"数据留在 GPU
- 达到"以磁盘容量为上限"的模型规模——TB 级模型理论可行

### 5.4 FSDP 与 ZeRO 的对比

**PyTorch FSDP**（Fully Sharded Data Parallel）——PyTorch 官方实现——理念同 ZeRO-3：
- 分片参数/梯度/优化器状态——按层包裹（wrap）——前向时逐层 unshard
- 与 Transformer 层封装深度集成（`fully_shard` 按层）
- 相比 DeepSpeed：社区维护活跃、与 `torch.compile`、activation checkpoint 兼容性好
- 选择建议：新项目优先 FSDP；需要 Offload/Infinity 或老生态时用 DeepSpeed

## 六、序列并行与其他维度

### 6.1 Megatron 序列并行（Sequence Parallelism, SP）

Transformer 中 LayerNorm/Dropout 的输入是 [batch, seq, hidden]——TP 切分后这两类算子在每卡重复计算——浪费显存。

**SP 做法**：LayerNorm/Dropout 的输出按 **seq 维**切分（本来是 hidden 维）——需要通信的算子（Attention/MLP 的 matmul）仍按 hidden 维——两个 f/g 边界做 all-gather/reduce-scatter。

- 节省：LayerNorm 激活冗余消除——对长序列显著
- 与 TP 共用通信组——不额外增加通信量

### 6.2 MoE 的 All-to-All

**MoE（专家混合）**——激活层"按 token 路由到不同专家"：
- 每个 token 属于哪个专家不确定——token 需要按专家分组**重排**（all-to-all 通信）
- 大规模 MoE 训练（DeepSeek-V3 671B 激活 37B）：
  - expert 并行（EP）：专家分布在多个节点
  - 每层 token 分派：all-to-all（M→N 卡交换）——通信量 = token 数 × 隐藏维 × 2
  - **通信与计算 overlap**：router 先算好分配表——先发"先行的 token 组"——后发的等计算
- 拓扑优化：DeepSeek 用 4 节点一组（EP=64 跨 16 节点×4 卡）——IB 域内 all-to-all 保持带宽

### 6.3 张量-流水线-数据-专家 的组合矩阵

```
DeepSeek-V3 671B 训练配置:
DP × EP × TP × PP（+CP）——双维混合（DualMoE 的细粒度专家 256 个）
每层: TP=8 组内 NvLink；EP 跨节点；PP 2 段；DP 大
MFU ≈ 45%（MoE 下）——通信占比 ~20%
```

## 七、通信优化：让 GPU 一直算

### 7.1 梯度压缩

- **梯度量化**：1-bit/8-bit 压缩梯度再 AllReduce（1-bit Adam 等）——通信量降 4~8 倍——误差补偿（error feedback）保证收敛
- **Top-k 稀疏化**：只传梯度绝对值最大的 k%——配合误差累积——理论保证收敛
- **选择时机**：通信是瓶颈时（跨数据中心/异构集群）才有价值——同节点 NvLink 场景收益小

### 7.2 通信-计算 Overlap（最重要）

- **DDP bucket 化**：梯度按 bucket 顺序算完即发——反向在通信中继续（默认已开启）
- **ZeRO/FSDP 逐层**：每层的 unshard/reduce 与下一层前向/反向重叠——"流水线化通信"
- **梯度累积 + 每步多 batch**：放大全局 batch——摊薄同步次数
- **MoE all-to-all 与计算重叠**：见 6.2
- **异步 checkpoint 存储**：保存权重的磁盘 I/O 与训练重叠

### 7.3 网络拓扑与集群设计

- **三层拓扑**：NvLink（机内 900GB/s H100）→ IB（机间 400Gbps）→ 数据中心
- **全局调度**：TP 必须同节点；EP 尽量同 IB 域；DP 随意
- **集合通信库**：NCCL（NVIDIA）/ RCCL（AMD）——支持 ring/tree/pipe 算法自适应
- 高水位实践：**IB 动态路由（SHARP）**——在交换机上做归约——进一步省带宽

### 7.4 显存优化（与通信配套）

- **Activation Checkpointing**：不存前向激活——反向时重算——显存 O(√L) 换取 30% 计算
- **激活重计算策略**：选择性（只 check 注意力/MLP 边界层）
- **混合精度**：bf16 权重 + fp32 主权重 + fp32 Adam——显存大头在优化器——所以 ZeRO Stage 1 性价比最高

## 八、大规模训练实践

### 8.1 训练数据管道

- **数据加载**：WebDataset 流式读取 + 多 worker 预取 + shard 预洗牌——不能让数据成为瓶颈
- **全局洗牌**：每 epoch 重新切分 shard——跨 rank 洗牌（不完全——成本高）
- **去重与质量过滤**（Dedupe、quality filters）——大模型性能的关键隐性因素
- **动态批处理**：按 token 数而非样本数组织 batch（训练效率提升 10-30%）

### 8.2 Checkpoint：训练的生命线

**Checkpoint 类型**：
- **全量 checkpoint**：模型 + 优化器 + 调度器 + RNG 状态——恢复后严格复现
- **sharded checkpoint**：每卡只存自己的分片（ZeRO/FSDP 标配）——恢复时按新拓扑重排
- **异步 checkpoint**：后台线程/进程写盘——不阻塞训练（崩溃时最多丢一个保存间隔）

**安全策略**：
- 循环保存（每 N 步覆盖）——保留最近 2~3 个 + 每周锚点
- **checkpoint 校验**：保存后做一次"加载 + 前向"冒烟测试——防静默损坏
- 存储：分布式文件系统（GPFS/WEKA）+ 本地 SSD 双写
- 大模型（万亿参数 bf16 ≈ 2TB）：**分片 + 压缩（fp16 转换、去重）**——恢复时间目标 < 10 分钟

### 8.3 故障恢复与容错

**故障模式**：GPU 硬件错误（HBM ECC、温度）、NIC 断链、节点掉电、OOM、训练发散（NaN）。

**容错策略**：
- **心跳监控**：master 定期收集 worker 心跳——超时判死——重启
- **弹性训练（Elastic）**：Torch Elastic / DeepSpeed 的 elastic 模式——动态加入/移除 worker——断点续训
- **自动重挂**：检测到 rank 死亡 → 全体杀 → 从最近 checkpoint 重载 → 重新建立集合通信
- **NaN 检测**：梯度聚合后检查——NaN 则丢弃该 step 并回退 checkpoint（"跳步"策略）
- **数据管道容错**：bad shard 自动跳过——不让一个坏文件搞崩全部

### 8.4 监控与可观测性

- **GPU 利用率/温度/功耗**：DCGM 指标——发现"冷卡"（通信等待）
- **训练指标**：loss 曲线、MFU、token 吞吐（tokens/sec）、通信占比
- **性能剖析**：NVIDIA Nsight Systems/Compute——定位 kernel 瓶颈
- **告警**：loss 突增/NaN/吞吐骤降——自动触发"暂停+回滚"
- **成本核算**：每 token 训练成本 = 集群成本 / 吞吐——优化目标是"每美元 token 数"

### 8.5 典型的万亿参数训练"配方"（综合案例）

```
以 1T 参数、1T token 为例的粗略预算:
FLOPs ≈ 6·N·D = 6 × 1e12 × 1e12 = 6e24 FLOPs
H100 集群: MFU 45%，FP8 理论 1979 TFLOPS → 有效 ~900 TFLOPS/卡
总卡时 = 6e24 / (900e12 × 3600) ≈ 1.85e6 卡时 ≈ 2000 卡 × 39 天
显存预算（每卡 80GB）:
  参数分片 (ZeRO-3/FSDP) + bf16 激活 + 重计算 → 恰好容纳
```

**工程口诀**：先小规模（1B/8 卡）把代码跑对 → 再按 3D/4D 放大 → 每翻 10 倍规模做一次"故障演练" → 上线前压测通信吞吐。

## 九、通信库与网络工程

### 9.1 NCCL 深入：从 API 到算法

**NCCL（NVIDIA Collective Communications Library）**——GPU 集合通信的事实标准：

```
常用原语:
  AllReduce     归约+广播（DDP 梯度同步）
  ReduceScatter 归约后每卡只留一块（ZeRO 梯度分片）
  AllGather     每卡收集全部块（ZeRO 参数收集）
  AllToAll      每卡给每卡发一份（MoE token 交换、Ulysses 注意力）
  P2P           点对点（流水线 stage 间传递激活）
```

**算法选择（自动自适应）**：
- **Ring**：带宽最优——但延迟随节点数增长——适合大消息
- **Tree**（halving-doubling）：延迟更低——适合小消息/跨机柜
- **Split（分片环）**：结合两者——多消息并行
- **NvLink 域感知**：机内 NvLink（900GB/s）与机间 IB（~50GB/s）——NCCL 按层级拆分通信路径
- **性能模型**：T(AllReduce) ≈ 2·α·log(N) + 2·β·(N-1)/N·M（α=延迟，β=带宽倒数）——用模型判断瓶颈

### 9.2 网络：IB vs RoCE vs TCP

| 方案 | 带宽/延迟 | 成本 | 生态 |
|------|-----------|------|------|
| InfiniBand（IB） | 400-800Gbps，微秒级 | 高 | NCCL 原生优化（RDMA） |
| RoCE（RDMA over Ethernet） | 类似 IB，需无损网络 | 中 | 成本优势明显 |
| TCP/多路径 | 慢一个量级 | 低 | 仅兜底/小规模 |

- **大模型集群标配 IB**——但 RoCE + 调优（PFC、ECN、拥塞控制）在成本敏感场景越来越流行
- **关键参数**：MTU/Jumbo frame、拥塞窗口、网卡队列——"99% 的网速由 1% 的配置决定"
- **拓扑**：Fat-Tree / Dragonfly——NCCL 的 tree 算法与之匹配
- 调试工具：`nccl-tests`（带宽/延迟基准）、NCCL_DEBUG、`nvidia-smi topo -m`（拓扑矩阵）

### 9.3 电力与散热：训练的另一半成本

```
万卡 H100 集群的账单:
硬件: ~$300M（H100 约 $3 万/卡）
电力: 每卡 ~700W → 万卡 7MW → 年电费 >$50M（$0.06/kWh）
散热: 液冷（直接冷却）比风冷省 30%+ 电费——新建集群标配
```

- **PUE（能源效率）**：1.1 液冷 vs 1.3+ 风冷——差 20% 电费
- **供电架构**：兆瓦级 UPS、柴油备份、储能——电网容量是选址的第一约束
- 密度：单机柜 100kW+ 液冷——机柜功率密度决定集群规模上限
- **节能技术**：动态频率（DVFS）、空闲节点下线、训练-推理错峰复用

## 十、真实案例复盘

### 10.1 GPT-3 175B（2020）——标杆方法论

```
配置: DP=64 × TP=8 × PP=8（3D 并行），V100 × 10K 卡
数据: 300B tokens，1536 全局 batch，3.5 个月
并行选择逻辑:
  175B 参数 bf16 = 350GB 权重 —— 单卡 32GB 放不下 → 需要模型并行
  TP=8 卡内 NvLink（机内）——PP=8 跨机（通信少）
  64 路数据并行复制 8×8=64 卡一组 → 总共 64×64=4096 卡（实际 10K 是实验和备用）
教训: 显存 → 并行度；带宽 → TP 规模；稳定性 → 训练时长
```

### 10.2 LLaMA 405B（2024）——BF16 + 大 PP

```
配置: 8K 卡（H100-80G × 8K），BF16，TP=8 × PP=8 × DP=128（近似）
要点: 全 BF16（不做混合精度主权重）——现代 GPU 的 bf16 足够稳
      FlashAttention-2 + 异步 checkpoint + 大 batch 课程
      训练 3.5 个月，消耗 ~3.9e24 FLOPs，MFU ≈ 40%
教训: 架构成熟后（GPU 原生支持 bf16）——训练配置趋于"标配化"
```

### 10.3 DeepSeek-V3（2024）——MoE + 极致成本

```
配置: 671B（激活 37B），FP8 混合精度，2048 H800 卡，2.788M H800 GPU 小时
创新点:
  - FP8 训练（scaled FP8 + 精细的 per-tensor/per-block 缩放）——首次大规模验证
  - 细粒度 MoE（256 专家 × 每 token 激活 8）——计算效率极限
  - 多头潜注意力（MLA）——KV 缓存骤降
  - 双管道 1F1B（PP=2 的流水线 + 跨节点 all-to-all overlap）——通信几乎全隐藏
成本: ~$5.6M（按 $2/卡时）——是 GPT-4 级训练的 1/10 以下
教训: 系统协同（架构 × 并行 × 精度 × 调度）——是成本优势的真正来源
```

### 10.4 失败案例的普遍教训

- **训练发散（loss spike）**：大多源于学习率/数据顺序——对策：梯度范数监控 + 自动回滚
- **静默硬件错误**：GPU 偶发位翻转——对策：定期校验（hash 权重）、训练-验证双路对比
- **网络抖动**：一条 IB 链路抖动——全体训练被拖慢——对策：多路径 + 快速重路由
- **checkpoint 过大导致停机**：万亿级恢复要数小时——对策：分片 checkpoint + 恢复时按需加载

## 十一、数据管道与训练调度

### 11.1 分布式数据加载：喂饱万卡

```
数据管道: 原始语料（PB 级）──→ 清洗 ──→ 去重（MinHash/SimHash）──→ tokenize ──→ 打乱 ──→ 训练
加载路径: 对象存储/Lustre ──→ 节点本地 NVMe 缓存 ──→ GPU 显存（三级流水线预取）
```

- **打乱原则**：跨文件打乱（全局随机）——同批次数据相关性是"隐性偏差"——防止模型学到数据顺序
- **去重**：MinHash 相似去重 + 精确去重——重复数据直接降低信息密度与评估可信度
- **混合采样**：多来源数据按配比混合（网页/代码/书籍/数学）——配比本身就是超参数——影响能力分布
- **异步预取**：数据加载必须与计算重叠（`num_workers`、prefetch）——否则 GPU 饿死——"数据是训练的第一瓶颈"
- **断点续读**：大训练的中断恢复要能从"数据位置"继续——而非从头重读——配套 checkpoint 的 epoch/step 记录

### 11.2 作业调度与容错：让训练"不会白跑"

```
万卡训练的残酷现实:
  单卡月故障率 ~1-3% → 万卡月故障 100-300 次 → 每 1-2 小时挂一次
  对策: 高频 checkpoint（分钟级/小时级）+ 自动重启 + 失败重放
```

- **调度器**：Slurm / Kubernetes（KubeFlow 训练算子）——资源配额、优先级、抢占
- **checkpoint 策略**：权重+优化器状态+数据指针 三合一；分片存储（每 rank 存自己那部分——避免集中写爆）
- **自动恢复**：检测到节点故障 → 重调度到健康节点 → 加载最近 checkpoint → 继续——目标"无人工干预"
- **心跳与健康检查**：GPU 温度/显存 ECC 错误监控——静默错误提前发现
- **训练-评估联动**：训练中定期跑 eval 集（保存 best checkpoint）——质量门禁而非只看 loss

### 11.3 跨集群与混合云：稀缺算力的最后一公里

- **混合云**：自有集群跑主力训练 + 公有云弹性扩容（突发任务、实验）
- **跨机房同步**：数据同步（对象存储就近缓存）、模型同步（梯度异步、周期全量同步）
- **联邦与去中心训练**：数据不出域 + 梯度共享——隐私场景（医疗/金融）的分布式训练形态
- **成本调度**：抢占实例（Spot）做实验、稳定实例做主力——错峰用电价
- 趋势：**"算力编排"成为独立学科**——把 GPU 当"水电气"来调度——利用率与成本双目标优化

## 十二、总结

```
单卡 ──→ DDP（数据并行，AllReduce）
          │ 模型放不下？
          ▼
       TP（切算子，机内） + PP（切层，跨机）
          │ 还是放不下？
          ▼
       ZeRO-3 / FSDP（全分片） + Offload（CPU/NVMe）
          │ 序列太长？
          ▼
       CP/SP（序列并行，Ring Attention）
          │ 通信太多？
          ▼
       梯度压缩 + overlap + 拓扑优化 + MoE all-to-all
          │ 会崩？
          ▼
       异步 checkpoint + 弹性容错 + 监控
```

**分布式训练的三条铁律**：
1. **显存决定"切法"**——模型多大用多深的并行——先分片再通信
2. **通信决定"部署"**——TP 绑定机内——EP 绑定 IB 域——DP 随处可放
3. **稳定性决定"产出"**——能 7×24 稳定跑完的简单方案——胜过纸面最优的复杂方案

AGI 的算力门槛——本质上是"分布式工程"的门槛。谁把 MFU 从 30% 提到 50%——谁就能用同样的电费多训 60% 的 token。下一阶段的方向：异构集群（GPU+TPU+自研）、稀疏训练（MoE 常态化）、超长序列（1M+ context）与"训练-推理一体"（test-time scaling 需要推理集群与训练集群同等规模）。
