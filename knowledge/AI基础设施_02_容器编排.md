# AI基础设施：容器编排与Kubernetes上的ML工作负载

## 1. Kubernetes GPU资源管理

### 1.1 NVIDIA Device Plugin的GPU分配机制

Kubernetes原生不感知GPU资源的存在。NVIDIA/k8s-device-plugin作为kubelet的Device Plugin gRPC端点实现了这一语义层。其核心流程始于Plugin的`Start()`方法向kubelet注册，随后即进入ListAndWatch主循环：通过nvidia-ml库枚举所有GPU设备并将每张GPU的UUID作为DeviceID注册；kubelet通过ListAndWatch gRPC流持续监听设备列表变化。当Pod请求`nvidia.com/gpu`资源时，kubelet触发Allocate调用，传入Container的Device请求（包括Request和Limit计数）。Plugin在Allocate响应中返回：环境变量注入（`NVIDIA_VISIBLE_DEVICES`设为特定GPU UUID集合）、设备节点映射（`/dev/nvidia0`等字符设备挂载入容器）以及额外的卷挂载（`nvidia_uvm`、`nvidiactl`等驱动层设备）[1]。这一机制的关键在于UUID与Container Device请求的一对一映射，保证了每个Pod获取到的是物理独立（或MIG分区）的GPU设备，不存在共享冲突。

然而Device Plugin仅解决资源暴露，不解决多个Pod对同一GPU的时分复用问题。标准分配方式下，`NVIDIA_VISIBLE_DEVICES`的环境变量策略（void/none/all或UUID列表）决定了容器对GPU的访问粒度。

### 1.2 MIG的分区调度

NVIDIA Ampere架构（A100/A30）引入的MIG通过硬件级分区将单张GPU切分为最多7个独立计算实例。在Kubernetes上以`nvidia.com/mig-profile`标签暴露资源。四种Profile的定义分别为：`1g.5gb`提供1个SM切片+5GB显存；`2g.10gb`为2个SM+10GB；`3g.20gb`为3个SM+20GB；`7g.79gb`为单卡全资源。调度器依据Pod的resources.requests与limits中的`nvidia.com/gpu`匹配节点上的`nvidia.com/mig-profile`标签完成静态调度[2]。

MIG在K8S上的调度分为两种模式。Static MIG Partition是目前成熟且推荐的生产模式：管理员在节点启动前通过`nvidia-smi mig -cgi`指令预配置好GPU的MIG分区拓扑，Device Plugin将这些分区直接暴露为独立设备。优势是所有Pod间的硬件隔离是物理级别的、性能可预测。Dynamic MIG Partition则处于实验阶段，允许运行时通过Device Plugin动态调整分区配置，但其依赖nvidia-ml的`mig/config`动态变更能力，目前Kubernete Device Plugin的Allocate流程尚不完全支持运行时分区重建的稳定语义。

MIG的关键限制在于：每个分区内的显存和计算吞吐被硬件隔离，但NVLink和PCIe带宽没有显式分区，因此当多个MIG实例同时访问跨GPU数据时可能出现带宽争用。

### 1.3 时间分片与GPU Sharing

MPS（Multi-Process Service）允许不同进程的CUDA kernel在同一个CUDA context上并发提交，由GPU的硬件work scheduler进行SM级别的时分复用。在K8S上部署时，通过共享DaemonSet将NVIDIA_VISIBLE_DEVICES设为同一UUID使多个Pod共享同一张GPU[3]。CUDA MPS Server充当代理，将来自多个容器的CUDA调用合并提交至GPU。

MPS的核心问题是隔离性严重不足。由于多个Pod共享同一个CUDA context：显存无隔离（任意Pod可OOM整个context）、地址空间共享、kernel执行队列非抢占。一个Pod的非法CUDA操作可能直接导致同GPU其他Pod崩溃。这种模式适用于批处理推理场景或开发测试环境，不适于多租户生产。vGPU方案（如NVIDIA vComputeServer）提供带显存和SM配额的虚拟化GPU，但其许可证成本和额外的hypervisor层开销限制了在K8S上的普及。

时间分片方案（如NVIDIA的Time-Slicing GPU Sharing）在Device Plugin层做时间片轮转：kubelet允许超量分配`nvidia.com/gpu`（Request/limits可超过物理卡数），Device Plugin在Allocate中为每个Pod分配同一UUID，但通过GUID的复用实现复用。较MPS而言，每个Pod仍享有独立的CUDA context且显存隔离，但无硬性显存保护（可被OOM Killer终止），且SM上下文切换带来显著的性能开销。

## 2. 训练作业的编排

### 2.1 Kubeflow Training Operator的架构

Kubeflow Training Operator通过CRD（Custom Resource Definition）扩展Kubernetes API来定义分布式训练作业。PyTorchJob定义了一个PyTorch分布式训练任务的拓扑，其Spec包括：

```yaml
spec:
  pytorchReplicaSpecs:
    Master:
      replicas: 1
      restartPolicy: OnFailure
      template: ...
    Worker:
      replicas: 4
      restartPolicy: OnFailure
      template: ...
```

Master和Worker的区分决定了`MASTER_ADDR`和`WORLD_SIZE`环境变量的注入逻辑——Master作为NCCL通信的协调节点。对于TFJob，引入了Chief/Worker/ParameterServer/Evaluator的四类角色。MPIJob则通过在Pod中注入`mpi.horovod.run`初始化器驱动OpenMPI的跨节点启动[4]。

PyTorchJob的Elastic Training实现基于`torch.distributed.elastic`机制。Operator通过`spec.nprocPerNode`和`spec.maxRestarts`控制Pod组的弹性扩缩。其核心是`elastic-agent`进程：Worker组内任意Pod失败时，elastic-agent会将对剩余的存活的Worker重新分配rank（重新执行`rendezvous`），而不是重启整个训练任务。这在K8S上表现为Operator不重建Pod组，而是等待MinSize条件满足后触发`rdzv`重新建连。从设计上看，PyTorchJob对Pod级弹性支持充分，但对节点级故障恢复需要配合Kubernetes StatefulSet的Recreate策略。

### 2.2 Volcano Gang Scheduling

Gang Scheduling（All-or-Nothing）是分布式训练的基本需求：一个训练任务的N个Worker Pod必须全部被调度后才能启动，否则部分Pod的启动并占用资源会导致死锁。Kubernetes的default-scheduler逐Pod调度，完全不满足这个语义。

Volcano的Gang调度通过三层抽象实现：Job（一组Pod的集合）→ Queue（资源配额域）→ PodGroup（调度时机粒度的编排单元）。调度流程为：1.用户提交的training job由Volcano Admission Webhook自动创建PodGroup CRD；2.Queue Controller将Job放入指定Queue；3.Scheduler开始调度流程——`PodGroupPhase`为`pending`→`running`的转换发生在所有Pod满足minMember时。Gang调度策略保证只有当PodGroup的所有minMember节点都找到可用资源的前提下，才会对任何一个Pod执行bind操作[5]。

Volcano的Backfilling优化：当高优先级Job占用部分资源但还不足以满足minMember时；低优先级Job使用空闲资源先行执行，而非让资源闲置。Backfilling通过`queue`的`weight`和`priority`参数的配合，设置各Queue的优先级权重，scheduler在预调度阶段扫描所有Queue中的待调度Job，优先选择高优先级Queue中可满足gang条件的Job，退而求其次选择低优先级Job进行回填。

### 2.3 批量任务的队列调度

Kubernetes的default-scheduler在分布式训练场景的不足体现在三个层面：1.逐Pod调度无视Job级约束；2.缺乏对GPU/CPU联合感知的Fair-Share调度；3.无preemption优先级。Volcano和Yunikorn通过队列调度机制补充了这些能力。

Queue的排序策略通常为Multi-Queue Fair-Share DRF（Dominant Resource Fairness）：调度器根据Job的dominant resource（训练场景通常为GPU）在所有Queue的占用比例进行公平调度。Priority抢占时，Volcano的Preempt动作不是简单删除Pod，而是触发PodGroup的状态回滚，将被抢占Job的Pod重新放回Queue待调度，同时维护`victimTasks`的调度历史防止优先级反转。

值得注意的是，Priority和Gang之间存在冲突可能：高优先级Job因minMember无法满足而阻塞，低优先级Job的Backfilling刚好占用了高优先级Job最小必要的资源。防止这类优先级反转需要管理员的Queue配置，在defaultqueue的`capability`限制下为每个queue设置严格的资源容量。

## 3. 推理服务的部署架构

### 3.1 Knative Serverless推理

Knative Serving为GPU推理Pod提供了基于请求并发的自动缩放（Concurrency-based Autoscaling）。在`autoscaling.knative.dev/class: kpa.autoscaling.knative.dev`和`autoscaling.knative.dev/metric: concurrency`参数配置下，Knative Pod Autoscaler（KPA）汇聚Request的并发统计，通过`Activator`组件实现对非活跃Revision的路由控制和缩放。

推理服务的Cold Start问题比HTTP服务严重得多。当GPU推理Pod从零扩展到一时，模型加载（GPT类大模型通常在5-30GB）需要数十秒到分钟级延迟。Knative的`scale-to-zero`策略需要配合`initial-scale: 1`和`scale-down-delay`参数进行调优，避免频繁的从零冷启[6]。实际生产部署中常设`minScale: 1`作为保底，配合HPA做40%-50% GPU util阈值触发scale up，同时通过`container-concurrency-target`限定每Pod最大并发请求数来预热。

Blobstore-Aware Scaling是一个有效的优化方式：将模型文件存储在NVMe本地SSD的hostPath上，Knative Pod通过initContainer以`wget`从GCS或S3拉取模型（利用readahead缓存），随后Triton Server仅需从本地加载，大幅降低cold start延迟。

### 3.2 Triton Inference Server的K8S部署

Triton的Model Repository可以在Kubernetes上通过两种方式配置。一是ConfigMap卷挂载：小模型（<500MB）的model config以ConfigMap挂载到`/models`目录。二是PVC挂载：大模型通过PV（通常是NFS或Lustre的ReadOnlyMany卷）挂载到所有推理Pod。

Triton支持多种Backend的混合部署——PyTorch（Python Backend通过Python进程运行）、TensorRT（直接加载.plan文件）、ONNX Runtime。它们的显存管理策略差异显著：

| Backend | 显存分配策略 | 支持Concurrent Model Execution |
|---------|------------|------------------------------|
| PyTorch | 惰性分配 + CUDA缓存管理 | 否（GIL限制） |
| TensorRT | 构建期显存池 + 运行时DAG调度 | 是（多个Execution Context） |
| ONNX | GPU版本依赖CUDA EP | 部分（需`session_options.intra_op`配置） |

Dynamic Batching通过`max_batch_size`和`dynamic_batching { preferred_batch_size: [4, 8] }`配置，Triton自动在max_queue_delay内聚合请求形成batch，有效提升GPU计算利用率。Concurrent Model Execution则是Triton的更强能力：单个GPU上不同模型的inference请求可以并发执行，由Triton的`sequence_batching`和`parallel_reservation`参数控制底层的CUDA stream并发[7]。

### 3.3 推理服务的高可用

推理服务的高可用设计依赖于反亲和调度（Pod Anti-Affinity）：

```yaml
spec:
  affinity:
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - podAffinityTerm:
          labelSelector:
            matchLabels:
              app: triton-server
          topologyKey: kubernetes.io/hostname
```

通过在节点拓扑上阻止同Label Pod的共置，确保任一节点故障不超过1/N推理容量。

HPA的双指标方案：以`custom.metrics.k8s.io/v1beta1`接入DCGM+Prometheus提供的GPU利用率指标和Istio/Knative提供的请求延迟P99。典型多指标HPA配置：`type: Object`的`gpu_utilization_percent > 60`和`type: Pods`的`request_latency_p99_ms > 200`任一触发即执行scale-out。scale-down策略设置`stabilizationWindowSeconds: 300`避免GPU利用率的抖动导致频繁扩缩。这种双指标架构有效兼顾了资源效率和延迟SLO[8]。

## 4. 存储与数据编排

### 4.1 训练数据的存储方案

对象存储（S3/MinIO）在弹性方面具有天然优势，但存在每次训练迭代的数据读取IO PPS瓶颈。分布式文件系统（Lustre/GPFS）在吞吐上远胜对象存储——Lustre通过MDS/MDT/OST的分布式元数据和数据布局将读写分散到多OSD上，但在K8S上运维复杂。

生产方案的常见分级存储架构是三层：1.冷存储层（S3对象存储，存储原始数据集和Checkpoint归档）；2.缓存层（计算节点本地NVMe SSD，通过InitContainer预热数据集）；3.热存储层（Lustre/GPFS PV，挂载给训练Pod，提供100GB/s级别的聚合吞吐）。

StorageClass的配置策略为：Tier-1使用`WaitForFirstConsumer`卷绑定模式并配合Local SSD的`volumeBindingMode: WaitForFirstConsumer`；Tier-2使用NFS/Lustre CSI的`Immediate`绑定模式。Pod通过PVC的`accessModes: ReadOnlyMany`进行数据的跨Pod共享读取。

### 4.2 StatefulSet的Checkpoint持久化

分布式训练的Checkpoint包含：模型权重（单机多Graph或多个Worker的各rank权重）、优化器状态、RNG状态、Dataloader offset。

PV存储策略：建议使用RWO（ReadWriteOnce）的块存储PVC（NVMe SSD backed），配置`reclaimPolicy: Retain`防止Pod删除后Checkpoint被回收。训练Pod通过`torch.save(state)`写入PVC上固定路径（如`/checkpoint/rank-{RANK}.pt`）。定期备份通过Velero的Schedule CRD和CronJob实现：每30min执行增量备份到S3[9]。

StatefulSet的Pod identity持久性对Checkpoint管理至关重要。利用StatefulSet的`pod-{ordinal}`命名规则，可将RANK映射到Pod序号，实现节点级灾难恢复后Checkpoint的精确还原。

### 4.3 I/O瓶颈的缓存机制

InitContainer预热数据是解决I/O瓶颈的有效手段。在主训练容器启动前，InitContainer执行以下流程：

1. 从对象存储或NFS读取数据集名称列表
2. 检查本地hostPath/SSD是否有有效缓存（通过checksum/content_hash比对）
3. 缓存缺失的文件通过`wget`或`aws s3 cp --recursive --max-concurrent-requests`并行拉取
4. 将缓存路径通过emptyDir或shared volume挂载给主容器

这种策略将冷数据训练首次epoch的IO延迟转移到了Pod启动阶段，不影响后续epoch的TFRecord/Parquet读取速率。对于大文件（超过100GB/epoch），可配置NFS的`fsc`参数在机架层面做FS Cache[10]。

IO瓶颈的更深层优化包括：使用PyTorch的DataLoader在worker进程中预读数据，配合`num_workers > 1`并行读取；Petastorm库直接读取Parquet格式的数据到Tensor/PyTorch Tensor而不经过中间格式转换；NVIDIA DALI直接在GPU上进行数据增强和预处理，完全避免CPU-GPU的IO瓶颈。

## 5. 网络与通信优化

### 5.1 Pod的网络性能

标准Kubernetes CNI（Calico/Cilium）的Overlay封装叠加了VXLAN/IPsec的隧道头部，增加延迟并限制MTU。对于分布式训练的AllReduce通信，这一Overlay开销是灾难性的——NCCL对通信延迟极其敏感。

hostNetwork模式直接使用Pod所在Node的主机网络堆栈，完全绕过CNI的Overlay封装。在hostNetwork=true的设置下，Pod直接通过Node的物理NIC（InfiniBand或RoCE）通信。InfiniBand的RC传输层提供零拷贝的RDMA Read/Write能力，NCCL通过`NCCL_IB_GDR_LEVEL`参数将GPU显存直接RMA到远端GPU显存，无需CPU内存中转。实测表明：在不使用hostNetwork的Overlay模式下，NCCL AllReduce带宽被限制在约30%的物理IB带宽，而hostNetwork直连模式下可达90%以上[11]。

### 5.2 RDMA over Kubernetes

NVIDIA Mellanox Network Operator通过Operator模式自动化管理RDMA网络设备。其组件包括：

- **SR-IOV Network Device Plugin**：将支持SR-IOV的Mellanox ConnectX网卡的VF作为可分配资源暴露给kubelet
- **Multus CNI**：每个Pod可附加多个网络接口——management网络（默认eth0, 用于Kubernetes API通信）和data网络（net1,  给NCCL通信）
- **RoCE网关**：RoCEv2的流控通过ECN/DCTCP配合Mellanox的Drop Count监控

Network Operator的部署流程为：安装MellanoxNetworkOperator CRD → 在MellanoxNetwork中配置`spec.deviceType： ConnectX6` → Operator自动生成`SriovNetworkNodePolicy` → Multus生成`NetworkAttachmentDefinition` → Pod在annotations中引用`k8s.v1.cni.cncf.io/networks: rdma-net`，设备自动注入。

RDMA Device Plugin（`nvidia.com/rdma`）将这些VF暴露为可分配设备资源，实现租户级别的RDMA资源隔离。

### 5.3 拓扑感知调度

NUMA-Aware训练要求的GPU、NIC处于同个NUMA节点。跨NUMA访问的PCIe通讯延迟增加约20-30%，严重影响AllReduce效率。

Kubernetes Topology Manager通过三种policy级别控制：1.`best-effort`——尽量匹配，不强制；2.`restricted`——必须匹配GPU和NIC在同一NUMA节点；3.`single-numa-node`——所有设备必须严格同一NUMA节点。

实现机制上，Topology Manager协调CPU Manager的CPU Pin策略和Device Manager的GPU分配策略。当kubelet接收到Pod调度请求（已由Kubernetes Scheduler分配Node）时，Topology Manager通过`HintProvider`接口获得GPU和NIC的设备拓扑亲和度（`NUMANodeAffinity`），若Pod配置`single-numa-node`而当前Node的GPU和NIC分布在不同NUMA，则拒绝Pod启动（Admit Failure）。调度器需配合Node的topology标签（`topology.kubernetes.io/zone`）在调度阶段就放置Pod到合适Node以减少Admission阶段的错误[12]。

## 6. 可观测性与运维

### 6.1 GPU Pod监控

GPU Pod的监控栈由三个组件构成：DCGM Exporter（暴露golang-nvml接口的Prometheus exporter）、Prometheus Server（聚合时序数据）、Grafana（可视化DashBoard）。

DCGM Exporter的指标体系围绕DCGM的GPU metric group展开。关键指标：

- `DCGM_FI_DEV_GPU_UTIL` —— GPU计算核心利用率
- `DCGM_FI_DEV_FB_FREE/USED` —— 显存占用
- `DCGM_FI_DEV_MEM_COPY_UTIL` —— 显存带宽利用率
- `DCGM_FI_DEV_POWER_USAGE` —— GPU功耗（热管控的关键指标）
- `DCGM_FI_DEV_NVLINK_BANDWIDTH_TOTAL` —— NVLink带宽

Pod级别的指标关联依赖`kube_pod_labels`和`kube_pod_container_resource_requests`的Kube State Metrics与DCGM指标通过`pod_name`和`kubernetes_pod_name`进行join。

### 6.2 训练作业的生命周期管理

分布式训练的错误定位是ML运维中最具挑战性的环节。Loki/ELK堆栈的日志聚合可在Loki中通过LogQL的`pattern`解析进行Pattern Detection——提取训练作业失败的Error类日志中的特定模式（如`RuntimeError: CUDA out of memory`、`NCCL WARN`、`Segmentation fault`等）并发送告警。

PyTorch Elastic的自动故障恢复机制细节：当worker失败时，Elastic Agent的`rdzv_handler`执行`rendezvous`重连。Torchrun的`--rdzv_backend=etcd`或`static`（默认c10d）。在K8S上使用`etcd`实现跨Pod的rendezvous是最稳定的方案：失败的Worker C被Group从`WORLD_SIZE`中移除，存活Worker通过`Barrier`确认新group，之后rank重新分配（Rank可以是本机持久化Checkpoint + 新Rank = 的映射）[13]。弹性训练的`min_size`和`max_size`参数控制可接受的Worker数量范围。

节点故障时，Kubernetes层面Pod被Scheduler分配到新Node，StatefulSet重新创建Pod（新hostname），etcd rendezvous中的`run_id`保持不变因此elastic-agent可将新Pod作为新Worker加入group。

### 6.3 GPU节点池的Autoscaling

Karpenter/Cluster Autoscaler在GPU节点伸缩的差异：Cluster Autoscaler基于Pendig Pod数量触发、支持AWS/GCP/Azure的托管节点组，但存在伸缩慢的问题（通常2-5分钟伸缩窗口）；Karpenter基于Simulator调度器实现毫秒级节点评估，直接调用EC2 RunInstance API，效率提升10倍以上。

Spot Instance的竞价中断处理：GPU Spot实例（如AWS p3.8xlarge Spot）在中断前2分钟发送`Spot Interruption Notice`（元数据中`termination-time`字段）。Operator可监听该元数据事件，触发Checkpoint的保存。

Checkpoint设计与Spot的配合：在Spot训练中，每隔`save_every_n_steps`步保存sharded checkpoint至PVC或S3。中断时Operator通过`preStop`钩子主动调用`torch.save()`，Elastic Training重新调度时从`last-checkpoint`目录恢复。由于Spot期间Checkpoint是异步存储，通常丢失不超过`save_every_n_steps`步损失[14]。

## 7. 新兴趋势——Kubernetes上的ML新范式

### 7.1 KubeRay

Ray的Kubernetes部署通过RayCluster CRD实现声明式管理。RayCluster中定义：

- Head Pod：运行GCS（Global Control Store）和Scheduler，是所有Ray worker通信的中心
- Worker Pod：运行具体的Python任务

Ray Operator保证了Head和Worker的自动发现和生命周期管理。位置感知调度通过`spec.rayCluster.spec.workerGroupSpecs[].template.spec.affinity`实现，保证需要GPU的Worker优先分配到GPU节点。

Ray的Object Store是跨越Node的大型对象分布式存储机制。每个Ray node上的Plasma Object Store通过共享内存mmap将Python的大的对象在Node上跨进程共享，Node间通过TransferManager的gRPC协议传输。该设计使得Ray在K8S上的分布式推理场景具有天然优势：模型参数在Head上加载后通过Object Store分发给各Worker，无需重复模型加载[15]。

### 7.2 NVIDIA DGX BasePOD / Kubernetes参考架构

NVIDIA DGX BasePOD是NVIDIA官方为DGX集群设计的Kubernetes参考部署方案。其Stack包括：

- **GPU Operator**：集成了k8s-device-plugin、DCGM Exporter、MIG Manager、GPU Feature Discovery等组件为一体，解决GPU节点驱动、Plugin部署、指标暴露的全生命周期。
- **Network Operator**：管理Mellanox ConnectX-7网卡的SR-IOV配置、RDMA Device Plugin和Multus CNI。
- **Cluster Policy (NVIDIA K8s Platform Team)**：提供Security Policy和RuntimeClass管理。

DGX BasePOD的优化方向集中在NCCL Fast Socket和local NVLink over Kubernetes的结合使用，通过Network Operator的`host-device` CNI使NCCL绕过Pod网络堆栈直接调用NVLink通信域实现跨节点通信。

### 7.3 无服务器Kubernetes的GPU演进

以Fly.io和Google Cloud Run GPU为代表的无服务器GPU容器正在改变推理部署的形态。这类平台的关键技术特征为：1.GPU Pod以微VM的粒度提供给容器运行时，每Pod独立GPU；2.从零到一的冷启动时间压缩至3-5秒（对比完整的K8S Pod冷启动25-40秒），通过将模型预加载到微VM的快照中实现近乎瞬时的模型加载；3.按秒计费的GPU使用单位极大提升利用率。

Serverless GPU的主要局限在于：不支持NCCL/RDMA多节点通信（MVMs之间无跨主机GPUDirect）、持久存储受限（仅Ephemeral Storage）、大规模训练场景仍依赖传统集群。其典型适用场景是CPU-only的推理和高并发的lightweight推理服务。

Kuberentes向Serverless的演进方向包括KubeVirt（用KVM粒度隔离Pod）、Knative的gRPC-Proxyless缩放到零的能力，以及WASM MicroVM在GPU推理中的探索性尝试。
